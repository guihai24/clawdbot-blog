假设你接手一个维护了两年多的项目。测试命令藏在旧脚本里，某个依赖必须锁定版本，格式化工具一跑就会改掉半个仓库。你把这些告诉 AI 编码 Agent，它第一次跌跌撞撞修好了问题。

第二天换个需求，你又开了一个新会话。它像刚进组一样，重新问测试怎么跑，重新把能用不能用的工具都翻一遍，最后卡在同一个报错上。

钱就是这么烧掉的。不是模型突然变贵，是你一直在给同一个 Agent 交「重复学费」。

---

## 同一个仓库反复用 AI，钱都花在哪了？

主要花在三类重复劳动上：重新摸索项目事实、加载用不上的工具、在失败路径里打转。成本大头不总是最终答案，而是 Agent 为了找到答案付出的上下文、工具调用和试错轮数。

Microsoft Research 这篇关于 TokenEconomizer 的研究，给出的不是又一个「更强模型」故事，而是一个更朴素的判断：<mark>Agent 在同一个仓库里工作，应该把经验留下来。</mark>

他们先看了一个很扎心的现象。在 SWE-Bench 的 60 个任务上分析 Claude Code，按仓库顺序跑任务。等一个仓库累计完成至少 5 个任务后，**30% 的工具调用重复了更早任务里的操作**；而与其他仓库历史匹配的操作只有 7%。

这说明大量浪费不是通用的，是「本地问题」。你的项目有自己的测试入口、构建怪癖、历史包袱，Agent 不知道，就只能每次重新考古。

还有一组数字更直白。Agent 每轮都会收到 23 个工具描述，但其中 16 个从没被调用。失败任务只占 17%，却吃掉了 32% 的费用。

说白了，跑偏的任务不是小事故，是账单里最粗的那根水管。

## TokenEconomizer 到底改了什么？

它没有把模型换掉，也没有要求开发者重写工作流，而是在会话结束后做三件事：把可复用的事实记成微技能、裁掉大概率用不上的工具、发现 Agent 卡死时提醒它换路。


![TokenEconomizer 的三大核心机制架构图](/images/posts/tokeneconomizer-agent-memory.svg)
第一件事叫微技能。名字听着玄，其实就是一行式项目笔记，比如「这个仓库用某个脚本跑测试」「某类改动要先同步生成文件」。它不是一次会话里看到什么就记什么，而是等多个会话反复确认某个模式后，才放进后续会话的起始上下文。后面如果有新证据反驳，这条笔记还会停用。

这点很关键。项目经验最怕的不是少，是过期。你让 Agent 记住一条三年前正确的命令，比不记还麻烦。TokenEconomizer 的处理方式像给笔记加了版本号：有证据才上，证据反了就撤。

第二件事是工具裁剪。研究报告里提到，Agent 每轮收到 23 个工具描述，16 个从没用过。工具说明不是免费塞进上下文的，每一轮都要占 Token。TokenEconomizer 会根据仓库历史判断哪些工具大概率用不上，把它们移出上下文，但保留运行命令和编辑文件这类核心工具。需要时还能恢复。

这里有个很实际的差别：<mark>减少工具不是限制 Agent 能力，而是减少它每次开会前必须读完的通讯录。</mark>真要找人，号码还在。

第三件事是失败循环干预。Agent 卡住时，常见表现不是停，而是用同一套参数反复撞墙。TokenEconomizer 会监测这种重复失败，让一个评判模型判断它是真卡住了，还是仍在推进。如果确实卡住，就给 Agent 一条简短提示，建议换方法。

开源插件里还有一个设计我觉得挺克制：如果 Agent 收到提示后仍然卡住，系统会通知开发者，而不是自己中止任务。这个边界很重要。省钱可以，别悄悄把活扔了。

## 它真能省钱，还是只在论文里好看？

研究里用 277 个真实缺陷修复任务、6 个仓库、5 种 Agent 与模型组合做了评估。结果是平均任务成本降低 18.4%–30.9%，所有测试过的仓库成本都有下降，任务成功率基本稳定，甚至部分组合的 Pass@1 还上升了。


![编码Agent随任务积累经验的成本下降趋势对比](/images/posts/tokeneconomizer-agent-memory-2.svg)
更值得注意的是节省随时间增长。从零历史开始，早期任务可能因为系统在学习和验证经验而更贵，但到第六个任务时，每个仓库的累计成本都低于默认水平。

这意味着它不是「第一次就神」的插件，而是越用越像熟悉项目的同事。

我也得把话说稳一点：这是论文和基准测试里的结果，不代表你在任何项目、任何 Agent 上都能复制同样的比例。项目结构、任务类型、工具数量、失败模式都会影响收益。尤其是只做一次性短任务的新仓库，历史经验积累不起来，效果自然有限。

但结论方向我认。<mark>降低编码 Agent 成本，不一定非要压模型能力，也可以先减少它重复做功。</mark>

降低推理强度也能省钱，研究里甚至有节省相近或更多的做法，但代价是性能明显下降。这就像让一个本来就不熟项目的人少想几分钟，账单也许薄了，返工可能厚了。

## 不想装插件，普通开发者能先做什么？

可以先做一个项目级 Agent 笔记，把重复事实、工具清单和失败模式写进仓库；然后连续跑一组同类任务，对比成本、成功率和重复操作次数。你不需要一开始就有完整系统，三份小文件就够起步。

我建议用一个很土但有效的结构：在项目根目录建一个 `AGENT_MEMORY.md`，不要让它是散文，让它像给下一位 Agent 交接。

```markdown
# Agent Memory

## 项目事实
- 测试命令：`npm test -- --runInBand`
-  lint 命令：`npm run lint`
- 生成文件改动后，需要重新执行：`npm run generate`
- 不要直接改 `dist/`，它会被构建覆盖

## 工具使用边界
- 常规查改文件：保留
- 运行测试：保留
- 浏览器工具：仅在 UI 任务中启用
- 部署相关工具：默认关闭，需要时手动开启

## 已知失败模式
- 遇到 `ENOENT: node_modules/.bin/vitest`：先安装依赖，不要反复改测试代码
- 修改 schema 后测试失败：先检查是否漏跑 generate
- 格式化导致大量 diff：只格式化本次触碰文件
```

这个文件的重点不是「写得全」，而是「写得更正」。每条经验最好带一个触发条件，比如「修改 schema 后」「遇到某个报错时」。没有触发条件的笔记，最后会变成一堆没人看的口号。

第二个动作是精简工具上下文。很多 Agent 默认把一堆工具全塞进去，方便是方便，但每轮都要付说明书钱。你可以先分两个工具集：

| 工具集 | 默认开启 | 适用场景 |
|---|---|---|
| 基础读写和运行命令 | 是 | 大多数缺陷修复、代码重构 |
| 测试和静态检查 | 是 | 需要验证改动的任务 |
| 浏览器和截图 | 否 | UI 调试、交互验证 |
| 部署和发布 | 否 | 明确要求上线或预发布时 |
| 数据库写操作 | 否 | 需要迁移或清理数据时 |

这不是说浏览器工具、部署工具没用。它们很有用，但不该每一次「帮我改个函数」都把它们请进会议室。

第三个动作是记录失败模式。别只记录成功方案，失败线索更值钱。尤其是一个任务已经连续几轮围绕同一个错误打转时，先让 Agent 输出三句话：现在卡在哪、已经试过什么、下一步准备换什么。

你可以直接用这个提示：

```text
如果你连续两次遇到同一个错误，暂停当前路径，先输出：
1. 当前失败的证据是什么；
2. 你已经尝试过哪些方法；
3. 有哪些尚未验证的替代路径。
不要重复执行相同参数的工具调用。
```

这套东西看起来不高级，但它抓住了 TokenEconomizer 的核心：经验不是一堆聊天记录，而是能被下一次任务直接消费的约束。

## Agent Memory 会变成新的技术债吗？

会。只要笔记由人长期维护，它就可能过时；只要笔记由 Agent 自动生成，它就可能把一次偶然成功当成普遍规律。所以关键不是「记不记」，而是让经验有生命周期。


![Agent经验生命周期与过滤机制](/images/posts/tokeneconomizer-agent-memory-3.svg)
比较稳的做法是给每条经验配三个字段：来源、确认次数、最近使用时间。来源说明它来自哪类任务，确认次数决定它够不够资格进入默认上下文，最近使用时间用来发现它可能过期。

一个最小模板可以这样写：

```markdown
- 规则：修改 schema 后必须运行 generate
  来源：任务 #12、#17、#23
  确认次数：3
  最近使用：2026-11-17
  状态：启用



我会把「确认次数」当成硬门槛。一条经验只出现过一次，先放候选区；出现三次以上，再进默认上下文。这和 TokenEconomizer 里「多个会话确认后才加入」的思路是一致的。

还有一个容易被忽略的点：Agent Memory 应该跟仓库走，而不是只躺在某个人的聊天记录里。放在仓库里，能 review、能 diff、能回滚。否则它就会变成另一位「只有老王知道」的项目玄学。

这也是我更看好这类方向的原因。过去我们优化 AI 编码，盯着的是模型分数；现在开始有人认真算另一笔账：Agent 在同一个项目里工作一年，到底能不能比第一天更懂事。

## FAQ

**Q: TokenEconomizer 一定要换模型吗？**<br>
A: 不需要。它的设计目标是在不改底层 Agent 和模型的情况下，用历史会话改进后续任务的上下文和提示。

**Q: 我的项目只开了几次 Agent 会话，值得做 Agent Memory 吗？**<br>
A: 可以先做轻量版。记录项目事实、测试命令和一次失败模式就够，等同一类任务重复出现后再补强。

**Q: 项目笔记是不是越多越好？**<br>
A: 不是。经验太多也会占上下文。优先保留被多次确认、能明确触发的规则，过期规则要及时停用。
