LocalLLaMA 版块上有人发了个链接。没有模型权重，没有训练脚本，只有一个 HuggingFace 数据集页面——12,121 次工具调用记录。

评论区第一条："挺酷，但 OpenAI 会把这当成蒸馏攻击。"

发帖的人回："我只是分享我的会话。"

另一个人接了句："AI 的输出不受版权保护，他们除了封号也做不了什么。"

这场对话里藏着两个信号。一个是法律边界的模糊地带，另一个更有意思：<mark>有人开始把「我怎么用 AI 干活」这件事本身，当成一种可以整理、打包、再分发的资产。</mark>

而绝大多数人的 AI 编程记录，还躺在某个隐藏文件夹里，等着被清理磁盘时顺手删掉。

---

## 这份数据集里装的到底是什么？

先说清楚它不是什么。它不是模型权重，不是训练代码，也不是那种几万条「问题—答案」的问答对。


![普通问答记录与工具调用轨迹的对比示意图](/images/posts/ai-coding-tool-call-dataset.svg)
它记录的是 Agent 干活的完整过程。这类数据在圈内有个名字，叫工具调用轨迹（tool call trajectory）——模型每一次读文件、改代码、跑命令、看报错的动作，连同动作的结果，被按顺序串起来。

一个具体的例子。假设你的测试挂了，你让 Agent 修：

| 普通问答记录 | 工具调用轨迹 |
|---|---|
| 你：这个测试为什么挂？ | 你：这个测试为什么挂？ |
| AI：可能是因为 mock 没有正确初始化…… | AI → `read_file(test_user.py)` → 返回 42 行代码 |
| （结束） | AI → `run_test()` → 返回 `AssertionError: expected 200, got 500` |
| | AI → `edit_file(app.py)` → 修改 3 行 |
| | AI → `run_test()` → 返回 `passed` |

左边那条记录，教会模型「怎么解释报错」。右边那条，教会模型「怎么修报错」。

差别看起来只是多了几行，实际是两种东西。前者是知识，后者是**行为**。

普通的聊天记录里，模型说的每句话都是「我认为应该这样」。轨迹里每个动作都跟着一个客观反馈——文件读出来是什么，命令跑完返回什么，测试过没过。这些反馈不是模型编的，是环境给的。

这就是为什么轨迹数据在训练 Agent 时更值钱：它能提供真实的因果链，而问答对只能提供语言模式。

## 为什么你的私有用量比公开语料更稀缺？

因为公开语料里全是「正确答案」，而真实工作中最有价值的部分是「错了之后怎么改」。


![私有数据价值对比：公开语料与本地纠错路径](/images/posts/ai-coding-tool-call-dataset-2.svg)
大模型厂商手上的通用代码语料，基本都是 GitHub 上那些最终被合并的 PR（代码提交审核）。它们干净、正确、结构漂亮，但没有过程。没人知道作者第一版写了什么，为什么推翻重写，中间踩了哪些坑。

你的本地会话不一样。你让 Agent 改一个函数，它改错了，你骂了一句，让它重来，它换了个思路，对了。这段来回里有三样东西是公开数据拿不到的：

第一是**你的判断标准**。什么算「能跑」，什么算「能上线」，你驳回它的理由往往是一句很土的话——「这样写线上会炸」。这句话模型在预训练里学不到，因为没人会把它写进博客。

第二是**你项目的上下文**。你的目录结构、命名习惯、内部工具链，这些东西构成了一个高度特化的环境。模型在你的环境里跑通了一个任务，这套跑通方式只对同类项目有效，但正因如此，它对你自己的价值极高。

第三是**纠错路径**。这是最容易被忽略的。第一次答对的样本，信息量其实很低——它只证明模型会。第一次答错、第二次改对的样本，才告诉模型「在什么情况下，什么做法会失败」。

<div class="callout callout-info">
💡 <strong>一个反直觉的推论</strong>：如果你想用自己的数据训一个专属小模型，只留下成功会话，训出来的东西大概率不如你直接用大模型。因为小模型的短板不是「不会做对」，是「错了不知道改」。
</div>

所以核心结论是这句：**你的私有数据不在正确答案里，在你驳回它的那一下。**

## 从零开始，怎么把散落的记录变成一份数据集？

发帖那位说自己能烧掉 25 billion tokens，是因为碰上了 Codex 的计费故障，拿到了无限额度。这个细节挺重要——它说明**你不需要这么大的量也能开始**。


![散落记录转为数据集的四个步骤流程图](/images/posts/ai-coding-tool-call-dataset-3.svg)
我记得看过一个人分享经验，说他只整理了几百条轨迹，训出来的小模型在自己的特定任务上就已经能顶一阵。数量不是门槛，结构才是。

下面四步是我拆出来的通用流程，按顺序走。

### 第一步：采集 —— 先搞明白你的工具把记录存在哪

现在主流的本地编程 Agent（Codex CLI、Claude Code、Cursor）都会把会话落盘在本地。位置不统一，但找法一样：在设置里搜 `session`、`history`、`transcript` 这类词，或者在用户目录下找隐藏文件夹。

判断标准很简单：**能不能导出成 JSON 或 JSONL**。如果只能导出成 Markdown 或者一段纯文本，那你得先写个小脚本把结构还原出来——标记每条消息的角色（用户 / 模型 / 工具返回）和时间戳。

有一个容易被忽略的点：**采集要趁早**。很多工具的会话有保留期限，或者超过一定长度会自动截断。我判断是这件事越早建立习惯越好——每周导一次，比攒半年再导要稳。

### 第二步：匿名化 —— 这步做不好，后面的工作全白费

Reddit 那个帖子里，发帖人特意感谢了另一位用户帮忙做 sanitisation。这个细节是整条帖子里最实在的部分。

匿名化不是简单地把名字换掉，要处理的东西按危险程度排：

```text
必查清单（按危险程度排序）：
1. API Key / Token  →  搜 sk-、ghp_、xoxb-、AKIA 前缀
2. 数据库连接串      →  搜 postgres://、mysql://、mongodb+srv
3. 内网 IP 和域名    →  搜 192.168、10.、*.internal、*.corp
4. 真实人名和邮箱    →  正则扫 @ 符号，人工复核
5. 客户名和项目名    →  换成语义等价的假名，别简单用 XXX
6. 绝对路径          →  /Users/你的名字/ 换掉
```

第五点要展开说。如果你把「美团」统一替换成「XXX」，那模型学到的是「XXX 是一家外卖公司」，这个语义就废了。正确做法是替换成 语义等价的假名：「某外卖平台」「某银行客户」。这样轨迹里的推理逻辑还成立。

判断标准：跑一遍上面六条的正则，全部零命中；再人工抽 20 条读一遍，确认读起来像是一个真实的、但属于虚构公司的项目。

### 第三步：清洗 —— 这一步决定了数据集的含金量

清洗不是「过滤坏的，留下好的」。恰恰相反，清洗的核心是分类。

我把它分成四类：

- 成功轨迹：任务完成，验证通过。留着，但别指望它教模型太多东西。
- 纠错轨迹：失败过，然后被修好。这是精华，优先级最高。
- 纯失败轨迹：试了几次放弃了。大概率要剔除，但如果失败原因很有代表性（比如「这个库根本没有这个 API」），可以作为负样本保留。
- 胡说轨迹：模型开始编造不存在的文件、不存在的函数。必须剔除，否则你会把幻觉一起蒸馏进去。

判断标准：每条轨迹结尾要有一个明确的终止状态。如果你自己都说不清这条会话是「成了」还是「黄了」，那它对模型也没有任何信息量。

### 第四步：分段 —— 按任务切，不按时间切

这是最多人做错的一步。

一个会话里可能干了三件不相干的事：修了个 bug、加了个接口、顺手改了个配置。如果你整段扔进去，模型学到的是一团浆糊。

正确的切法：一个任务 = 一个可验证的目标 = 一个明确的结束状态。

怎么判断切得对不对？拿切好的片段单独看，问自己一句：「如果我把这一段交给一个新人，他能明白要做什么吗？」能明白，切对了。不能，说明这段还粘着上一个任务的尾巴。

到这里，数据集的骨架就有了。但骨架不等于能用。

## 怎么验证你做出来的数据集是真能用？

有一套很朴素的检验方法，不需要跑训练就能做。


![AI数据集清洗与验证的五大核心步骤](/images/posts/ai-coding-tool-call-dataset-4.svg)


第二，看任务分布。 统计一下你的轨迹里，有多少是「改 typo」级别的琐碎活，有多少是「实现一个新功能」。如果九成都是前者，这份数据集训出来的模型只会改 typo。真实的工作分布应该是长尾的——绝大多数任务很简单，但你必须让简单任务不占据绝对多数。



第四，反查一遍敏感信息。 别只信自己第一步的正则。拿最终版本再扫一次，尤其是模型在轨迹里「引用」出来的那些内容——它可能把你文件里的密钥原样打在了回复里，而你的第一步只扫了输入，没扫输出。

第五，抽 10 条人工读。 随机抽，从头读到尾，问自己：「这条轨迹如果被别人看到，我会不会尴尬？」会，就说明清洗没到位。这个标准比任何技术检查都有效。

<div class="callout callout-warn">
⚠️ <strong>关于授权的那条评论</strong>：Reddit 上有人担心这是「蒸馏攻击」，也有人反驳说 AI 输出不受版权保护。这两边都有道理，但都不构成你的免责声明。如果你的记录来自公司项目，先看劳动合同和工具的 TOS（服务条款）——大多数人只看前者，忽略了后者明确禁止用输出训练竞争模型。
</div>

## 这份数据集能拿来干什么？

说三个不夸张的用途。

一是做 few-shot 示例。 这个门槛最低，不需要训练。你把整理好的轨迹挑出三五条最典型的，作为示例塞进 system prompt。模型看到「原来在这个项目里，改代码是先读测试再改实现」，它的行为会立刻收敛。这件事今天就能做。

二是训一个专属小模型。 适合任务高度重复的场景——比如你的项目里有一类固定的重构模式，一周要干好几次。用小模型跑这类活，成本和延迟都下来。前提是你得有足够的同类轨迹，几百条起步。

三是当团队的知识资产。 新人接手项目，最痛苦的不是看不懂代码，是不知道「这个项目里遇到这类问题该找谁、该改哪」。一份整理好的轨迹，比一份文档更接近真实工作流。

至于变现，我不太想给一个具体数字。这条路的现实是：数据集本身很难直接卖钱，值钱的是「你有能力把混乱的工作过程整理成结构」这件事。这个能力可以拿去做咨询、做课程、做定制 Agent——但那是另一篇文章的事。

## 最后一句

回到那个 Reddit 帖子。发帖人说自己「只是分享了会话」，语气挺轻松。但底下那些讨论蒸馏、版权、TOS 的评论，说明这件事已经在灰色地带里了。

我想说的不是「赶紧去导出数据」，而是：你每天和 AI 协作的过程，正在产生一种以前不存在的资产。它现在没有明确定价，也没有明确规则，但它确实存在。

删掉它只需要一次磁盘清理。留下它，只需要每周花十分钟。

这个选择，我觉得不难做。

## FAQ

Q: 我不是重度用户，记录量很少，还有必要整理吗？<br>
A: 有必要，但方法不同。量少的时候不要想着训模型，直接把最典型的几条轨迹整理成 few-shot 示例塞进 prompt，当天就能见效。

Q: 用 Codex 或 Claude Code 的记录做数据集，会违反服务条款吗？<br>
A: 取决于用途。自己用、做内部工具通常没问题，拿去训练竞争模型基本都被禁止。动手前把 TOS 里关于 output 和 training 的条款读一遍，别只看劳动合同。

Q: 整理一份能用的数据集大概要多久？<br>
A: 第一次最慢，因为要建流程。采集和匿名化脚本跑通之后，后续增量维护每周十几分钟。别指望一次做完，把它当成一个持续的动作。
