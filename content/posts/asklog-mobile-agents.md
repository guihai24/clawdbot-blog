假设你同时开了三个 AI 编程任务。

一个在重构登录模块，一个在给后台加导出功能，还有一个正在修数据库查询。三个任务都跑得挺好，直到它们同时停下来，等你回答问题。

第一个问数据库字段要不要兼容旧版本，第二个问导出文件应该用 CSV 还是 Excel，第三个发现原来的接口和新需求有冲突。

你人正在外面吃饭，电脑在家里亮着。

**AI 编程最大的效率损耗，正在从「写代码太慢」变成「人类回复太慢」。**

这也是 asklog 试图解决的问题：让 AI 编程助手在后台继续干活，把真正需要你决定的事情推到手机上。

## AI 编程为什么越来越需要一个「项目经理」？

过去用 Claude Code 或 Codex，工作方式很简单：


![AI 编程从传统单兵作战到“老板-项目经理-执行者”的多级协作架构对比](/images/posts/asklog-mobile-agents.svg)
打开终端，描述需求，等它执行，检查结果，再给下一条指令。

一个任务还好，三个任务就开始混乱。

你得记住每个窗口在做什么，哪个任务遇到了问题，哪个已经完成，哪个正在等你确认。任务越多，切换成本越高。

这里有个容易忽略的变化：**AI 编程工具的瓶颈，已经不只是模型能力，而是人类的协调能力。**

想象一家只有一个老板的小公司。

老板不可能亲自完成每份工作，于是把不同任务交给员工。员工负责执行，遇到需要拍板的事情再来找老板。老板只需要处理决策，不需要盯着每个人敲键盘。

asklog 的思路基本就是这样。

它的产品介绍里出现了两个角色：

- **Chief**：接收你的整体任务，负责拆分工作、协调编码代理。
- **Workers**：实际执行任务的 Claude Code 或 Codex 工作进程。

你只需要告诉 Chief 一件事，它就会把任务拆成多个子任务，交给不同的编码代理执行。

而你不需要一直待在电脑前。

## asklog 是怎么把多个 AI 编程任务管起来的？

最值得关注的设计，不是手机通知，而是它给每个 Worker 准备了独立的仓库副本。


![asklog 独立仓库副本的多 Worker 协作架构图](/images/posts/asklog-mobile-agents-2.svg)
这解决了多代理协作中一个非常现实的问题：**多个 AI 同时修改同一个项目，很容易互相踩脚。**

比如你让三个代理分别做：

| Worker | 任务 | 主要修改范围 |
|---|---|---|
| A | 重构登录模块 | `auth/` |
| B | 增加数据导出 | `export/` |
| C | 优化数据库查询 | `db/` |

如果三个代理直接操作同一个工作目录，A 可能正在修改公共接口，B 已经按照旧接口写完了调用逻辑，C 又顺手改了相关的数据结构。

最后你面对的不是三个完成的任务，而是一锅需要人工排查的代码。

asklog 的产品介绍明确提到：每个 Worker 都在自己的仓库副本中工作。

这意味着它们可以各自修改代码，不必直接争抢同一份工作目录。

这里可以把它理解成装修房子：

- Chief 是项目经理，负责分配施工任务。
- 每个 Worker 拿到一套独立施工图。
- 你是业主，负责验收和决定哪些方案可以采用。

**独立工作区解决的是执行冲突，人工审批解决的是决策风险。**

这两个环节缺一不可。

需要说明的是，仓库副本隔离并不代表所有冲突都会自动消失。不同 Worker 仍然可能修改相互依赖的模块，最终合并时依然需要处理 Git 冲突、接口兼容和测试失败。

## 为什么手机才是这套工作流的关键？

很多 AI 编程工具已经可以在后台执行任务。


![AI编程工作流：手机处理决策与电脑执行的协作模式](/images/posts/asklog-mobile-agents-3.svg)
但后台执行不等于无人值守。

真正麻烦的是任务中途需要人做决定。

比如一个编码代理发现：

- 新功能需要修改数据库结构。
- 原有接口没有覆盖某个特殊情况。
- 当前实现方案可能影响其他模块。
- 两种实现方式都能完成需求，但维护成本不同。

这时模型可以提出建议，却不应该默认拥有最终决定权。

asklog 把这类决策带到手机上，让你跨设备查看任务、回答问题。

整个工作流可以拆成下面几步：

<mark>你负责决定做什么，AI 负责执行怎么做，最终合并仍然由你批准。</mark>

1. **提交整体任务。** 在 Chief 中描述目标，例如「给后台增加订单导出功能，同时保证现有筛选条件正常工作」。
2. **等待任务拆分。** Chief 将整体需求分成多个子任务，启动 Claude Code 或 Codex Workers。
3. 并行执行。 每个 Worker 在自己的仓库副本中完成对应工作。
4. 手机处理决策。 Worker 遇到需要你判断的问题时，将问题交给你，你可以远程回答。
5. 检查执行结果。 任务完成后查看各个 Worker 的产出。
6. 授权合并。 只有得到你的授权，改动才会进入合并流程。

这套设计把人的工作从持续盯进度，变成按需处理决策。

以前你可能需要每隔几分钟切回电脑，看一眼终端有没有停住。现在可以把注意力留给真正需要判断的事情。

当然，手机审批也不是让你在地铁上审查几百行代码。

它更适合处理有明确上下文、能够通过简短回答解决的问题。涉及数据库迁移、权限系统、支付逻辑等高风险改动，还是应该回到电脑上完整检查。

## 多代理并行，哪些任务值得交给 asklog？

这里我想强调一个判断：

不是任务越复杂，就越适合拆给更多 AI。真正适合并行的任务，是彼此之间有清晰边界的任务。

举个例子。

你准备给一个已经上线的 SaaS 增加团队管理功能。

可以拆成：

| 子任务 | 是否适合并行 | 原因 |
|---|---|---|
| 增加团队管理 API | 适合 | 有明确接口边界 |
| 开发团队管理页面 | 适合 | 可以根据约定接口独立开发 |
| 编写相关测试 | 有条件适合 | 需要先约定预期行为 |
| 修改全局用户权限模型 | 谨慎 | 可能影响多个模块 |
| 数据库迁移 | 谨慎 | 涉及共享数据和部署顺序 |

如果任务之间存在大量依赖关系，强行并行反而会增加沟通和合并成本。

我更倾向于把 asklog 这样的工具用在三类工作上：

第一类：功能边界明确的开发任务。

例如后台增加一个独立报表模块，前端页面、数据查询和测试可以分开推进。

第二类：代码审查与修复。

让不同 Worker 处理不同模块的问题，减少一个代理同时理解整个项目的负担。不过最终修复仍然需要统一验证。

第三类：耗时较长的后台任务。

例如代码重构、文档补齐、测试覆盖率提升。它们不需要你每分钟盯着进度，但中途可能需要确认实现方向。

不太适合的场景也很明确：需求本身还没想清楚、多个任务都要修改同一个核心模块，或者涉及无法轻易回滚的生产环境操作。

这些工作不是多开几个 AI 就能解决的。

## 手机远程审批，怎么避免 AI 越权？

这部分我认为比「手机上能不能收到通知」重要得多。

因为当你不在电脑前时，AI 的自主行动范围越大，出错后越难及时发现。

asklog 的产品介绍有一句非常关键：

Nothing merges without your authorization.

也就是没有你的授权，改动不会被合并。

这是一个值得独立开发者借鉴的设计原则：把执行权和最终批准权分开。

但要注意，允许 AI 执行任务，不等于允许 AI 随意操作整个项目。

如果你准备搭建类似的工作流，可以直接复制下面这份授权规则，作为给 Chief 的任务约束。

```text
你负责协调多个编码代理完成开发任务。

授权边界：

1. 可以在独立仓库副本中修改代码。
2. 可以运行本地测试和静态检查。
3. 可以阅读项目文件和现有文档。
4. 遇到需求歧义时，必须向我询问。
5. 修改数据库结构前，必须获得我的批准。
6. 修改认证、权限、支付相关代码前，必须获得我的批准。
7. 禁止直接向生产环境发布代码。
8. 禁止未经授权合并分支。
9. 每个任务完成后，提供修改文件、
   实现说明、测试结果和已知风险。

最终合并必须等待我的明确授权。
```

这份规则不是 asklog 的官方配置，而是一套可以迁移到其他 coding agent 协作流程的管理约定。

还有一个细节值得单独强调：手机上的「回答问题」和「批准代码合并」应该是两种不同权限。

你可以允许 AI 根据你的回答继续执行，但不应该让它把一次普通的需求确认，自动解释成对所有后续修改的授权。

例如：

- 「使用 CSV 格式」只代表确定导出格式。
- 「可以修改数据库字段」只代表允许这项变更。
- 「批准合并」才代表允许将经过检查的代码合入目标分支。

权限拆得越清楚，远程管理就越放心。

<div class="callout callout-warn">
⚠️ 手机审批不是代码审查的替代品。 特别是涉及数据删除、权限变更、支付和生产环境时，必须保留测试、人工检查和回滚方案。
</div>

## asklog 对独立开发者意味着什么？

我觉得这类产品有一个比远程控制更值得关注的方向：

一个人管理多个 AI 编程代理，正在从「多开几个终端」转向「管理一支数字团队」。

以前一个独立开发者的产能，很大程度上取决于自己能同时处理多少事情。

现在编码代理可以并行工作，但人的注意力依然只有一份。

所以接下来真正有价值的工具，未必是让 AI 再快一点，而是帮人处理任务分配、进度协调、异常上报和最终授权。

asklog 展示的就是这个方向。

不过，我也不想把它说成已经解决了所有问题。

从目前公开的产品介绍，可以确认它支持 Chief 拆分任务、启动 Claude Code 或 Codex Workers、独立仓库副本、手机查看与回答，以及未经授权不合并。

但公开素材没有提供足够信息来确认具体收费、支持的手机推送渠道、离线审批能力、并发上限和完整的冲突处理机制。

这些都是实际采用之前应该核实的事项。

如果你准备尝试，可以从一个低风险项目开始：

1. 选择一个不涉及生产数据的代码仓库。
2. 给 Chief 一个能够拆分的完整需求。
3. 观察它是否能合理拆分任务，而不是把一个大任务机械切成几块。
4. 检查 Workers 是否真的在独立仓库副本中工作。
5. 故意设置一个需要人工确认的决策点，观察手机端能否及时处理。
6. 检查最终结果，确认没有未经授权的合并。
