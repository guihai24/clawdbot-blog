很多人盯着 AI 写代码的速度，真正顺手的用法却反着来：别让它一口气做完整任务，把每轮改动压到几秒能看见结果的大小。

你在编辑器里对 AI 说：「把这个后台首页重新设计一下。」它开始生成，光标缩进，页面没变化，终端跑着一堆工具调用。你等了一分钟，它说做完了。你扫一眼，布局能看，但按钮位置不对、颜色太跳、间距像没调完。于是你再写一段更长的补充说明，再等一轮。

这个循环重复两三次，你会有种奇怪的感觉：明明它在飞快生成 token，你的手感却像在排队。

我判断，打断心流的重点不是等待时长本身，而是你从「看见变化—立刻判断—马上调整」的节奏里被踢出去了。这跟以前在 DevTools 里拖 CSS 的状态刚好相反：你当时并不知道最终要什么，靠的就是即时反馈一点点试出来。

OpenAI 开发者最近分享的 Codex Ultrafast 用法，值得看的不是速度数字，而是它把 AI 编程从「下发任务后离开」重新拽回「边看边改」的做法。相关产品公告见 [OpenAI Developers Blog](https://developers.openai.com/)。原文提到，本周发布的 GPT-6.2 Astra 和 Sol Ultrafast 在 Codex 里 token 生成最快提速 <mark>4.5×</mark>；Sol Ultrafast 在 200 美元 Pro 计划里可用，API 促销按 3× Standard 定价，而非 6×。⚠️ 价格和可用范围可能变化，实际以官方页面为准。

## 为什么你让 AI 写代码时总觉得像在排队？

因为你在用一个「离线交付」的流程，做一件本来需要「在线试探」的事。


![交付任务与探索任务的流程对比图](/images/posts/codex-ultrafast-flow.svg)
UI、幻灯片、文案、表格这类任务，有个共同点：你在动手前通常只有一个模糊方向。不知道按钮放哪儿才顺手，不知道标题重一点会不会压住正文，不知道动画快半拍是不是更舒服。这类问题没标准答案，只能看一眼、改一点、再看一眼。

可你给 AI 的却是一整段完整需求：页面结构、交互逻辑、样式风格、响应式细节全塞进去。它只能赌一个最像「完成品」的结果。赌中了，你省事；赌不中，你重新描述，等待下一轮。高推理和长任务在这里未必帮忙——它只是在帮你更认真地猜一个你自己还没想清楚的东西。

我把这种状态叫「把探索任务包装成交付任务」。表单填写、批量改名、按文档补测试，这类目标明确、验证标准清晰的事，适合整包下发；界面微调、文案语气、信息密度，这类「我看了才知道对不对」的事，必须把决策权留在过程里。

一个很直接的判断法：如果你无法在任务开始前写出明确的验收标准，那就别下发大任务。先让它做一个能看见的最小版本，再围着这个版本改。

## 快速迭代的核心：把大任务拆成几个「看得见」的小循环

这套工作流可以迁移到任何带预览、带编辑、带 API 输出的场景。它不依赖某个按钮，依赖的是你把循环设计成什么样。


![快速迭代五步小循环流程图](/images/posts/codex-ultrafast-flow-2.svg)
![快速迭代循环](/images/posts/codex-ultrafast-flow.svg)

我把它拆成五步。重点不是工具多新，而是每一步做完你都能立刻看到反馈。

1. **先把结果放到屏幕上**

   做 UI 时，确保项目跑着带热重载的 dev server，也就是改完代码不用整包重建、页面会自己更新的本地服务。你改一行样式，页面应该立刻变化；如果每次都要手动刷新、重新构建，这个循环从一开始就不成立。

   预览最好留在应用内浏览器或分屏里，紧挨着 AI 对话。别让结果藏在终端输出里。做对了你会看到什么？你输入「把卡片间距从 16 改成 24」，页面马上跟上，而不是只看到一段「已修改」的文字回复。

2. **一次只给一个小反馈**

   把「重新设计首页」拆成连续的小句：「顶部导航太挤，左右内边距加大」「主按钮换成更暖的橙色」「这张卡片标题压到两行，改成单行截断」。每句话只对应一个可见变化。

   Ultrafast 真正有用的地方，就是让这些小改动在几秒内出来。你不需要每次都写完整背景，因为页面就在那儿，AI 和你共享同一个上下文。任务越小，生成越快；生成越快，你越能连续给反馈。

3. **指向具体位置，别写作文描述**

   能用标注就别用文字。框住那个按钮，再说「这个」，比写「页面中部偏右那个主要操作按钮」省事得多。没有标注功能时，给元素加稳定的 data 属性或局部截图，也比大段方位描述靠谱。

   我倾向把它当成一次代码评审：你不会在 PR 里写「这里不太对，你猜一下」，你会点在具体那一行。给 AI 的反馈也该这样——**保持其他区域不变，只改我指到的地方**。

4. **低推理起步，复杂点再升档**

   这类小反馈通常不需要高推理。原文作者的做法是从 Light/Low reasoning 起步，碰到更细微的判断——比如设计一个动画的节奏——再临时切到 High，完事后降回来。

   这里的逻辑很朴素：改内边距、换颜色、调整文案长度，考的不是深度推理，而是执行明确指令的速度。把高推理留给真正需要权衡的地方，速度和成本才不会互相拖后腿。

5. **验证后置，别每改一次都跑全套**

   小视觉改动阶段，先让 AI 只写代码，你自己盯浏览器确认。全量测试、lint、跨端检查放到你满意那一版之后再跑。原文把这个顺序说得很直接：快速循环里别塞不必要的验证。

   但要留个边界。这个做法适合「看一眼就知道对不对」的改动；涉及权限、支付、数据迁移的任务，验证不能后置。心流很重要，线上事故更重要。

## 什么时候快速模型真的有用？

答案取决于你这一轮在等什么：等模型生成，还是等工具跑完。


![快速模型收益对比：等模型 vs 等工具](/images/posts/codex-ultrafast-flow-3.svg)
很多人把速度体感直接等同于「模型快」。但一次任务的总时长里，token 生成只是一段。构建、编译器、测试套件、图片生成、外部接口，这些时间的瓶颈跟推理速度无关。原文举过一个很实在的例子：让模型改一行代码、跑增量构建和 18 个测试，整条链路里模型生成只占一部分。编译要多久还是多久。

| 场景 | 快速模型的收益 | 原因 |
|---|---|---|
| UI 微调、样式迭代 | 明显 | 改动小、预览即时、验证主要靠肉眼 |
| 文档段落修改、幻灯片逐页调整 | 明显 | 反馈连续，上下文已在手边 |
| 表格填充、简单表单 computer use | 较明显 | 动作短，且能写脚本批量处理 |
| 大构建、全量测试、编译 | 有限 | 时间主要花在工具上，不在 token 生成 |
| 图片生成任务 | 有限 | 图片生成本身耗时，模型只能加速周边步骤 |
| 需要一夜长跑的复杂实验 | 不明显 | 你本来就不盯着屏幕，速度不决定体验 |

<div class="callout callout-info">
💡 <strong>先分清你等的是模型，还是等工具</strong>：如果一轮对话的大部分时间花在 build、test、compiler 或图片生成上，Ultrafast 不会让整件事快上 4.5×。它加速的是生成与反馈之间的那段路，不是整条流水线。
</div>

这个区分对 API 用户尤其重要。原文给的方向是：文档已经在上下文里的摘要和问答、快速工具调用、computer use 里的表单填写、语音交互后端，这几类更容易吃到速度红利。如果你已有 API 流程，可以试着把 `service_tier` 设为 `ultrafast`，然后测一次完成时间，而不是只看首 token 时间。

还有一个容易被忽略的点：computer use 里，**别让 AI 用「人手点按钮」的方式做本来可以批量处理的事**。原文提到，如果应用支持 code mode，模型可以写一段脚本填完多个字段，而不是每个字段来回一次。这也是一种「小步快跑」——不是动作更快，而是把循环缩短。

## 这套方法怎么迁移到你的日常？

你不需要为了它换掉整套工具链。先挑一个你经常反复改的东西：落地页、组件库样式、README 措辞、给客户发的周报模板。把它的反馈循环改短。

我整理了一份可以直接复制的提示词模板，核心是限制范围、要求可见变化、把验证留到最后：

```text
只改我指出的这一处，不要动其他区域。
本轮目标：{一句话描述可见变化}。
完成后告诉我改了哪个文件和哪几行。
先不要跑测试或构建，我会先在预览里确认。
```

如果你做的是 API 产品，这份清单更实用：

| 判断项 | 适合快速迭代 | 不适合快速迭代 |
|---|---|---|
| 任务目标 | 模糊，要看结果才知道对不对 | 明确，验收标准能提前写完 |
| 反馈方式 | 标注、截图、逐段评论 | 一次性完整需求文档 |
| 验证成本 | 肉眼或单条请求就能确认 | 全量测试、编译、多系统集成 |
| 用户是否在等 | 屏幕前持续互动 | 后台长跑，第二天看结果 |
| 推荐节奏 | 低推理 + 短任务 + 后置验证 | 高推理 + 整包任务 + 严格验证 |

这份清单不是让你全程开最快。它的作用是帮你决定：现在这一轮，到底该追求速度，还是该追求确定性。

快速模型最舒服的状态，是让人重新进入那种「我想看看这样会不会更好」的手感。你不是把任务丢出去然后等交付，而是坐在副驾驶位上，每几秒给一次方向。模型负责手速，你负责品味。

两者的分工一旦摆正，等待感就会少很多。

💡 <strong>今天就能做的一件事</strong>：把你正在做的一个 UI 或文档任务，拆成 5 条「一句话反馈」。每条只改一个可见点，改完不跑全量检查，先看结果。你会发现自己更愿意一直盯着屏幕了。

## FAQ

**Q: Ultrafast 只适合 Codex 用户吗？**<br>
A: 不是。速度只是条件，核心方法是短任务、即时预览和连续反馈。你在任何带预览的编码工具里，都能先照这套循环调整工作方式。

Q: 低推理会不会让代码质量变差？<br>
A: 改颜色、间距、文案这类明确指令通常够用。涉及架构权衡、复杂动画或权限逻辑时，再切到高推理，不要全程省。

Q: 什么时候不该把验证后置？<br>
A: 涉及支付、权限、数据库迁移、接口兼容的任务不该后置。视觉和文案可以先看效果再验证，关键业务逻辑必须先验证再合并。
