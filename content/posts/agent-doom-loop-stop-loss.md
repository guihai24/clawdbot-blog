21:40，Agent 接到任务：查一张发票的总额。

21:41，账单服务的工具调用超时，错误被写回对话。

06:12，它还在试。同一个工具，同一串参数，第 41 次。任务没完成，账单完成了。

这份时间线来自 OpenRouter 在 11 月 12 日发的[一份实测教程](https://openrouter.ai/announcements)，他们写了个只会失败的工具，把这件事从头到尾跑了一遍。我把那六组数据翻完之后，最想说的不是「记得设上限」——<mark>是他们测出来的东西，比「Agent 会循环」这件事本身要拧巴得多。</mark>

## Agent 死循环为什么会越跑越贵？

一句话回答：**因为每一轮都把所有失败重新发一遍。轮数线性增加，上下文按轮累加，账单的增速快过轮数。**


![Agent 死循环导致 Token 指数级膨胀的流程图](/images/posts/agent-doom-loop-stop-loss.svg)
一次运行里，OpenRouter 逐轮记了输入量：第一轮 131 个 Token，到后面涨到 3,262 个。中间多出来的部分，几乎全是前面每一次失败的错误信息。二十多倍，而这才只是十几轮。

原因不复杂。模型不请求工具、直接给出回答，Agent 循环才会结束。一个持续失败的工具，恰好让它没有理由这么做：错误被塞回对话，系统提示里仍然写着「完成任务」，那再试一次看起来就是唯一正确的下一步。整个循环里没有任何代码在数它试了几次。

所以那 41 次，其实不能怪模型。演示用的系统提示写得很直白：

```text
You are a billing agent. Complete the task.
If a tool call fails, retry it.
Do not stop until you have the invoice total.
```

它只是在执行指令。而且它每一轮都知道超时了——最后那句回答里明明白白写着「服务连续 30 秒超时，共尝试 41 次」。知道，照试，因为指令里没留下「放弃」这个选项。

单看这一跑，成本 $0.0309，好像也就一杯便利店咖啡。但这是 flash 级模型、单会话、41 轮。把它换成贵的模型，再乘上并行跑着的十几个会话，就是原文说的那个场景：一夜几千美元。

## 六模型实测：两种失败，只有一种会叫醒你

同一套 Agent，六个模型，各跑三次，开启和关闭检测各一遍。


![死循环的两种结局对比图](/images/posts/agent-doom-loop-stop-loss-2.svg)
| 模型 | 无防护（3 次调用的工具调用数） | 触到 40 步 | 开检测后（3 次调用的工具调用数） |
|---|---|---|---|
| claude-haiku-5.5 | 6 / 6 / 6 | 0/3 | 2 / 2 / 2 |
| deepseek-v4.1-flash | 6 / 5 / 7 | 0/3 | 2 / 2 / 2 |
| gemini-3.8-flash | 5 / 6 / 5 | 0/3 | 2 / 2 / 2 |
| mistral-large-4-0 | 11 / 41 / 41 | 2/3 | 2 / 12 / 2 |
| gpt-6-luna | 17 / 37 / 21 | 0/3 | 2 / 2 / 20 |
| grok-4.7 | 41 / 12 / 41 | 2/3 | 2 / 2 / 2 |

这张表最容易被误读成「检测有用」。它真正的信息量在左边一栏。

前三个模型会在五六次之后自己停下来，交一句「任务失败，服务持续超时」。后三个会一路顶到 40 步上限，中途还夹着 11、12、17 这种跑法。

看起来是前三个更省心，对吧？

**恰恰相反。** 前三个才是真正难防的：它们不报警。你早上去看日志，语气平静、格式规整、结论清晰，你甚至会以为是自己给的工具有问题。41 次那种反而好办，账单刺眼，你一定会去查。

这就是我一直觉得这件事里最容易踩空的地方——<mark>死循环有两种结局，一种吵醒你，一种让你以为任务完成了。</mark>

还有一个细节值得单独拎出来：grok-4.7 三次跑，同样输入，分别调用了 41 次、12 次、41 次。所以「我测过一次，没问题」这句话在循环面前是无效的。循环是个概率事件，不是配置错误。

## 为什么只设步数上限不够？

因为步数上限不是刹车，是油量表的红线——它告诉你烧完了，但不会让车停下来。


![步数上限机制的四个核心漏点可视化图解](/images/posts/agent-doom-loop-stop-loss-3.svg)
四个具体的漏点：

**一是它允许你跑到最贵那一步。** 40 步上限，意思是你允许它一路烧到上下文最长的第 40 轮才收手。前面说过，到那会儿单轮输入已经涨了二十多倍。上限越宽，你付的那一刀越贵。

**二是触发时那一次调用照样执行。** 原文专门提了：上限触发时，模型已经请求的那次调用 SDK 仍会跑完。所以 41 步上限，实际是 41 次调用。这个差一，在成本统计里经常对不上账。

**三是它分不清「合理重试」和「死循环」。** 网络抖动第一次超时、第二次成功，那是对的。可它和「同一个坏工具试 40 次」在上限眼里长得一模一样。

**四是它只管一个会话。** 你有 20 个任务并行跑着，就有 20 条独立的油量表，各自烧到各自的红线。

不过比账单更麻烦的，是上下文。41 条一模一样的超时错误堆在历史里，就算你手动把这个任务救回来，这个会话也基本废了——后面无论问什么，模型都带着「这个工具是坏的」的偏见在说话。止损的第二重价值在这里：它保住的不只是钱，是会话还能继续用。

## 不换框架，这四层怎么加进去？

先说位置。前两层在工具层，第三层在循环层，第四层在账户层。越靠前越便宜，越靠后越保命。


![AI Agent四层防御体系架构与成本阶梯](/images/posts/agent-doom-loop-stop-loss-4.svg)
<div class="callout callout-warn">
⚠️ <strong>关键区别</strong>：前三层是让任务<em>正常结束</em>——失败，但你知道。第四层是让损失<em>有上限</em>——它救不了任务，只能救你的信用卡。只装第四层，等于每次都等截肢。
</div>

### 第一层：给重复做一个指纹

不依赖任何 SDK，在工具执行外面包一层就行。核心是给「工具名 + 参数」算一个 key，连续计数，到阶梯就升级处理。

```ts
const streaks = new Map<string, number>();
const LADDER = { observe: 2, block: 3, stop: 6 };

function norm(v: unknown): string {
  if (typeof v === "string") return v.trim().toLowerCase().replace(/\s+/g, " ");
  if (Array.isArray(v)) return v.map(norm).join(",");
  if (v && typeof v === "object")
    return Object.keys(v).sort().map(k => `${k}=${norm((v as any)[k])}`).join("&");
  return String(v);
}

async function guardedCall(
  name: string,
  args: any,
  run: (a: any) => Promise<any>,
  loopKey?: (a: any) => string,
) {
  const key = `${name}:${loopKey ? loopKey(args) : norm(args)}`;
  const n = (streaks.get(key) ?? 0) + 1;
  streaks.set(key, n);

  if (n >= LADDER.stop) throw new Error(`DOOM_LOOP_STOP ${key} ×${n}`);

  if (n >= LADDER.block) {
    return `ERROR: 你已用相同参数调用 ${name} ${n} 次，结果不会改变。不要重试。` +
           `换一种方法，或者直接说明为什么必须重复这次调用。`;
  }
  return run(args);
}
```

有两个细节值钱。

**第一，拦截时返回的错误话术，必须明确写「重试无用」。** 原文那句对比很精准：超时错误会让模型觉得再试一次有意义，而「你在重复自己」这条错误直接告诉它没有。多数模型读到这句，下一轮就写出最终答案了。

**第二，同一轮里的并行重复只算一次。** 模型一口气发五个一模一样的调用，那是它还不知道结果，不算循环。只有它已经看到上一次结果、又发了一次，才计数。

阶梯的三档对应三种动作：2 次只观察记录，3 次开始拦截，6 次直接终止整轮。默认这套阈值偏保守，你要是想更早收手，改成 `{ observe: 2, block: 3, stop: 4 }` 就行——原文用这个配置让一次 GPT-6 Luna 的运行在连续重复 4 次时结束，花费 $0.0002。

### 第二层：防止它换个马甲继续试

这是最容易漏的一层，也是原文里最意外的部分。

被拦截之后，模型会听话地「换一种做法」——但只有一个工具时，它能换的只有参数写法。于是出现这种日志：

```text
fetch_invoice("INV-2291")   → block (streak 3)
fetch_invoice("2291")
fetch_invoice("inv-2291")
fetch_invoice("INV2291 ")
```

每次都是一个新指纹，连续计数从零重新开始。原文里 Mistral Large 4 在九次开启检测的运行中这么干了五次，其中三次愣是顶到了 40 步上限；GPT-6 Luna 用的是尾随空格和换行。

解法是给工具声明「哪个字段才是身份」：

```ts
loopKey: ({ invoice_id }) => invoice_id.replace(/\D/g, "")
```

所有变体都映射到 `2291`，计数继续往上走，重复继续被拦。加上这个之后，同一次运行从 13 次调用降到 2 次，花费从 $0.0125 变成 $0.0039。

说白了就是：判断重复的不能是字符串，得是你语义上认为的「同一件事」。 订单号、URL 路径、文件绝对路径，都该做归一化。

### 第三层：双上限，步数和钱一起卡

```ts
let spent = 0;
const MAX_STEPS = 30;
const MAX_COST = 0.5;   // 美元

for (let step = 1; step <= MAX_STEPS; step++) {
  const res = await callModel({ /* ... */ });
  spent += res.usage?.cost ?? 0;
  if (spent >= MAX_COST) break;
}
```

两个上限要一起设，原因很实在：步数上限不知道模型多贵，费用上限不知道还剩多少步。少一个都会留缺口。

阶梯还有两档默认关着的，需要时可以打开：`steer` 会主动给模型发一条提示，说它在重复自己；`escalate` 会把下一轮交给一个更强的模型来跑。后者要小心，换了更贵的模型又没停，成本曲线会更陡。

### 第四层：在账户上封顶

前三层全在你自己的代码里，代码有 bug 就一起废。所以最后一道得放在供应商那边——给 API 密钥设一个额度上限，请求超了直接返回 402，来源标成密钥限额。

它救不了任何任务。它救的是那个凌晨三点没人看日志的你。

## 上线前跑这三个测试

别等真出事。用一个必然失败的假工具，把这三件事各验一遍。



第三个测试最容易忘，也最容易出问题。预算中断的路径上，得保证状态被写下来——不然你只会看到一个没有结果、也没有错误的任务。

## 上限设太紧，会误杀正常的重试吗？

会。网络抖动第一次超时、第二次成功，这是合理的，不该被算法当成循环。

所以阈值不能设成 2。观察档放在 2、拦截放在 3，这个间距是有道理的：给一次「真·瞬时限流」的重试留了口子，从第二次开始记录，第三次才动手。

真正拦不住的是另一类——软循环。模型不再调同一个工具，而是换着工具、换着策略绕圈子，指纹检测完全看不见它。这类只能靠第三层的费用上限兜。

所以四层不是四个可选项，是四种失效模式的对应：指纹管「不知道自己在重复」，归一化管「知道但换写法」，双上限管「任何原因的失控」，账户额度管「代码本身有 bug」。缺哪一层，对应的那种死法就没人管。

---

41 次重试的那次演示，模型每一轮都清楚服务挂了，仍然继续试。它没错，它只是没有被告知「可以停」。

我倾向认为，Agent 的成本控制最后会变成像数据库索引一样的东西——没人会因为「我的查询挺快」就不建索引，但今天大部分 Agent 还在裸奔。真要动手，不用一次上四层。先加第一层，拿一个必然失败的假工具跑一遍。等你在日志里第一次看到那句「你在重复自己，重试无用」，这条路就算通了。

## FAQ

Q: 换个更强的模型能解决死循环吗？<br>
A: 不能。模型每轮都在正确执行「工具失败就重试」这条指令，问题不在推理能力。实测里温和的模型会在五六次后安静交差，倔强的会顶到上限，没有一个会自己换策略。

Q: 步数上限设多少合适？<br>
A: 按任务复杂度定，常见是 20 到 40 步之间，同时必须配一个费用上限。只设步数的话，上限越宽，你付的那一刀越贵，因为上下文是逐轮累积的。

Q: 不用 OpenRouter SDK，这些方法还有用吗？<br>
A: 有用。四层里前三层都是你自己代码里的事：工具层包一层计数、参数做归一化、循环里累加 usage。只有第四层在供应商那边，换成你用的平台的额度或预算功能即可。
