凌晨两点，你让 Agent 查一个偶发 500 的接口。它翻了日志，盯着一段缓存代码看了半天，说「可能是并发竞争」。你让它证明一下，它又改了三四处地方，跑了一遍测试——通过。你正准备收工，线上又报了一次同样的错。

它不是不聪明。它只是把「猜」当成了「查」。

我更愿意把问题定义成：**在复杂排查里，Agent 缺的从来不是下一步动作，而是外部记忆和验证纪律。** 一位做了二十年软硬件逆向的老手，在 Hacker News 上分享了他的 LLM 辅助工作流（https://news.ycombinator.com/ ），里面最值得普通技术人抄的，不是那些专业工具，而是两件很朴素的事：让 Agent 一路写 MD 笔记，以及卡住时强制走「假设—实验—验证」循环。

---

## Agent 为什么会绕圈子？

因为它把对话历史当成了记忆，把「说得通」当成了「验证过」。


![Agent 绕圈子成因与笔记刹车机制图](/images/posts/agent-hypothesis-debug.svg)
对话上下文是有限的。排查越长，前面的关键线索越容易被压缩、被新内容冲淡。Agent 第二次看同一个问题时，常常已经忘了第一次排除了什么，于是又把老路走一遍。更麻烦的是，模型天然擅长生成「听起来合理的解释」，如果你只要一个答案，它就给你一个最顺口的故事，而不是一个能被证伪的判断。

那位老手的办法很硬：从分析二进制结构开始，就命令 Agent 把每一条发现写进 MD 文件。这些文件给自己看，也给 Agent 看。它们的作用不是留档，是给下一轮推理一个不会被聊天上下文冲掉的锚点。

我判断这一步对做接口排查、脚本分析、固件研究的人都成立。你换成任何复杂问题，道理都一样——**笔记不是产出，是刹车**。

---

## 为什么一定要写进 MD 文件？

因为文件是唯一既便宜、又能跨会话存活、还能被机器直接读写的「长期记忆」。


![三份排查笔记文件的结构与职责分工](/images/posts/agent-hypothesis-debug-2.svg)
我建议把排查笔记固定成三份，放在项目根目录的 `investigation/` 下面。别写散文，按事实、假设、证据分栏，Agent 读起来才像在查表，而不是在考古。

```text
investigation/
├── MAP.md          # 结构认知：入口、分支、依赖、关键函数
├── FACTS.md        # 已确认事实：命令输出、日志片段、实验结论
└── HYPOTHESES.csv  # 假设登记表：每次只测一个，写明证据与状态
```

`MAP.md` 回答「这东西大概怎么运转」。`FACTS.md` 只写已经被证明的东西——日志里实际出现的报错、某次实验的真实输出，别把推论混进去。`HYPOTHESES.csv` 是核心，后面会讲。

这里有个很容易踩的坑：不要让 Agent 一边猜一边往 `FACTS.md` 里写。事实区和假设区必须分开，否则几轮之后，整份笔记就会变成一堆「可能、大概、看起来像」，反而加固了偏见。

原文里那个逆向工作流还提到一个细节：遇到卡住时，他会去读完整的对话轨迹和思考过程，凭经验判断 Agent 是不是钻进了死胡同，然后手动换方向，比如从「跟交叉引用」改成「跟字符串」。这一步靠的是人的经验，机器自己很难做。但前面三份文件，能把这种人为干预的次数压下来。

## 假设实验法到底是什么？

它是把「猜」改造成「判案」的一套纪律：**一次只提一个可验证的假设，设计一个能明确证明或推翻它的实验，把结果写回表格，再决定下一步。**

原文作者把这个做成了公开的 Agent 技能，叫 hypothesis-debugging（https://github.com/ioma8/hypothesis-debugging ），流程很克制：Agent 卡住时，先写一条假设进 CSV，然后设计一个「决定性实验」——探针、日志、断点都行——要求这个实验必须能给出明确答案，而不是模棱两可的观察。

三个文件里，`HYPOTHESES.csv` 长这样就够用：

```csv
id,hypothesis,experiment,expected_if_true,result,status
H1,缓存键未区分租户,构造两个租户请求打印缓存键,键相同,键含tenant_id,REJECTED
H2,超时由重试放大,关闭重试后压测并发,错误消失,仍偶发,INCONCLUSIVE
```

关键在 `expected_if_true` 这一列。它逼你把话说死：「如果假设成立，我应该看到什么」。写不出这一列，说明假设还不够具体，不能拿去测。

区分一下bad case和good case：

| 写法 | 问题 | 改法 |
|---|---|---|
| 可能是并发问题 | 无法证伪 | 把并发数从 5 降到 1，错误是否消失 |
| 大概缓存没清 | 「大概」不是判断 | 打印缓存键和过期时间，看是否符合预期 |
| 也许是依赖版本 | 范围太大 | 锁定到上一版本跑同一组用例，结果是否一致 |
| 应该加个日志看看 | 没说看什么 | 在入口和分支各打一条，验证参数是否传入 |

原始工作流里还有一个很实用的补充：当单纯的反汇编/反编译走不通时，他会给 Agent 换工具——设断点调试、启用日志、注入探针记录运行时数据，或者干脆给它一个能控制的模拟器。这里的共同点是，**不再让它「继续想」，而是让它「去做个实验」**。

说白了，Agent 绕圈不是因为想得不够多，是因为没被要求用证据说话。

<div class="callout callout-tip">
💡 <strong>卡住时的切换口令</strong>：别再说「再想想」「换个方向试试」。直接说「停，写一条可验证假设到 HYPOTHESES.csv，并设计一个能明确证明或推翻它的实验」。模糊指令会换来模糊尝试。
</div>

## 哪些场景适合用这套方法？

适合有明确结构、能观测中间状态、且错误可复现的问题；不适合一次性问答、纯创意任务，或者根本拿不到日志和探针的黑盒。

我判断它最适合三个特征同时出现的场景：

- 问题有多个可能原因，而且原因之间会互相伪装，比如「缓存」和「重试」都会造成偶发超时；
- 你能控制实验条件，能改配置、打日志、加断点、注入探针；
- 排查会跨越多轮会话，或者会换不同的 Agent 接手。

反过来，如果是一个从未见过的全新领域，连结构都不清楚，第一步不该是提假设，而是先把 `MAP.md` 做出来。原文作者也是先让 Agent 识别二进制类型、平台和构建信息，再分析主要函数和分支，有了基本结构图才开始往下钻。没有地图就做实验，跟蒙眼开车差不多。

还有一件事我得说稳：这套方法不会让 Agent 变成专家。原文把「读对话轨迹、凭直觉判断它跑偏了」列为需要你自己具备的技能。工具和模板只能减少瞎猜，真正的判断力还是在你这边。

## 今天就能照着做的最小版本

不用装任何插件，先做三步：建目录、写第一份 `MAP.md`、把下一次卡住时的假设写进 CSV。

你可以直接复制这段，作为 Agent 卡住时的提示词：

```text
你现在卡住了。停止继续猜测和改代码。

1. 在 investigation/HYPOTHESES.csv 新增一行：
   - hypothesis：一句话写清楚你认为的原因，不接受「可能/大概」
   - experiment：设计一个能明确证明或推翻它的实验（日志/断点/探针/对照配置）
   - expected_if_true：如果假设成立，会看到什么具体现象
2. 只执行这一个实验，把真实输出写进 result。
3. 根据 result 把 status 标为 CONFIRMED 或 REJECTED。
4. 如果结果是 INCONCLUSIVE，说明实验不够决定性，重写实验，不要换假设。
```

给任务开头再加一句更省事：「先把已确认事实写进 investigation/FACTS.md，再开始分析；任何推论必须等实验确认后才写入。」

这套东西看起来土，像是在让 AI 填表格。但它把一个极易滑向玄学的排查过程，强制变成了可回溯的记录。就像办案一样——线索归线索，推理归推理，定案靠证据。

如果你也在盯一个反复出现、每次都「好像找到了又没找到」的问题，今晚不妨先别让它继续跑。让它把已知事实写下来，然后问一句：你现在的假设是什么，你打算怎么证明它是错的。

## FAQ

**Q: 这套方法一定要用逆向工具吗？**<br>
A: 不用。MD 笔记和假设表是通用方法，接口排查、脚本调试、数据问题都能用，只是探针形式不同。

**Q: Agent 卡住时直接让它换思路不行吗？**<br>
A: 「换思路」太模糊。给出可验证假设和实验条件，Agent 才知道往哪里换，也才能留下可复查的记录。

**Q: 每个人都要建那三个文件吗？**<br>
A: 不必。只有跨会话、多轮排查的问题值得建；简单一次性任务，写一条假设就够了。
