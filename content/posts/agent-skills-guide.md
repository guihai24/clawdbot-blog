每周一，你把「查上周新增用户、排除测试账号、生成一份给运营看的日报」重新讲给 AI。

下周一，数据源换了、报表格式改了，你再讲一遍。到了周五，临时来一个新人接手，又从头解释一次。明明是同一套流程，却散落在聊天记录、Prompt 和某个人的记忆里。

我更愿意把它看成一次没被保存的代码提交：今天能用，明天还得重新写。

GitHub 在 11 月 13 日发布的 [Agent Skills 指南](https://github.blog/) 给出了更合适的容器：把任务说明、触发条件和执行方式放进一个带版本的目录，以 `SKILL.md` 为中心，让不同 Agent 复用。

它不替你拿数据库权限，也不会自动创造一台服务器。它做的是更朴素但更重要的事：<mark>让你脑子里的重复操作，变成团队可以检查、修改和传递的文件。</mark>

---

## Agent Skills 到底是什么？

一句话回答：**它是放在目录里的任务说明书，告诉 Agent 什么情况下使用这项技能、需要哪些输入、应该产出什么结果。**


![Agent Skill 目录结构与三大核心要素](/images/posts/agent-skills-guide.svg)
一个最小的技能目录，大致长这样：

```text
daily-user-report/
├── SKILL.md
├── scripts/
│   └── generate_report.py
└── references/
    └── metric-rules.md
```

`SKILL.md` 不是一段万能提示词，而是一份任务合同。它最好只负责一件事，并把三件事写清楚：

| 部分 | 要回答的问题 | 示例 |
|---|---|---|
| 触发时机 | 什么时候应该调用？ | 用户要求生成新增用户日报时 |
| 输入 | 执行前必须拿到什么？ | 日期范围、数据源名称、排除规则 |
| 输出 | 怎样才算完成？ | Markdown 报告、CSV 明细、异常说明 |

GitHub 官方示例里的 Proof Agent 更强调「独立验证」。AI 写完代码后，再由另一个验证者检查错误声明、代码问题和安全风险。技能说明中有一条很硬的原则：自己检查自己，不算真正验证。

这件事比「让 AI 再检查一遍」可靠。写代码的 Agent 如果同时提交解释，它可能把自己的判断带进复核；独立验证者只看原始需求和代码改动，才能发现两个版本之间有没有偷偷对齐答案。

**技能的价值不是多一层措辞，而是把「什么时候做、拿什么做、交什么结果」从聊天里搬出来。**

## 第一份 SKILL.md 怎么写？

假设你每周都要生成新增用户日报。目标不是一次写出一个万能 Agent，而是先抓住重复率最高、规则最稳定的那个动作。

### 1. 先写触发条件，而不是先写操作步骤

很多技能失败在开头写成了说明书：

```text
首先打开数据库，然后查询用户表，接着计算新增用户……
```

这样写的问题不是不具体，而是没有边界。Agent 可能在不该运行的时候运行，也可能漏掉真正需要它的地方。

更稳的写法是：

```yaml
---
name: daily-user-report
description: 生成指定日期范围内的新增用户日报，排除测试账号，并输出运营可用的 Markdown 报告与 CSV 明细。
---
```

`description` 不是宣传语，而是 Agent 判断「要不要加载这项技能」的索引信息。触发条件最好包含明确动作和交付物，不要写成「处理数据相关的任务」这种大而空的描述。

### 2. 把输入写成可检查的条件

日报任务至少需要日期范围和数据源。还要明确缺少什么时应停止：

```text
输入要求：
- start_date：必填，格式 YYYY-MM-DD
- end_date：必填，不能早于 start_date
- source：必填，必须存在于项目配置中
- test_account_rule：可选；未提供时读取项目配置

如果 source 不存在，停止执行并列出可用数据源。
```

这一段比「请根据用户需求判断」可靠。模型可以处理模糊表达，但你的重复流程不应该把关键输入也模糊掉。

### 3. 用输出契约结束任务

Agent 很容易在「已经做完主要工作」后继续解释一串，报告却没生成。输出契约可以规定交付物、结构和失败状态：

```text
成功时必须生成：
1. daily-user-report.md：包含统计区间、总量、趋势和异常说明
2. daily-user-report.csv：每个用户一行的明细
3. summary.json：包含日期范围、数据源和排除规则

缺少必要输入时：
- 不生成空报告
- 返回 MISSING_INPUTS
- 列出缺失字段及示例值
```

我把这个叫作「可验收的结尾」：不是写一句「请生成日报」，而是规定读者拿到文件后，怎样判断任务真的完成了。

<div class="callout callout-tip">
<strong>写技能时先问一句</strong>：如果同事只拿到这份 SKILL.md，他能不能照着交付同样的结果？如果答案是否定的，缺的不是更多提示词，而是输入、边界或验收标准。
</div>

## 多个技能怎么协作，才不会越写越乱？

单个技能适合边界清楚的动作。涉及数据迁移、发布或指标管线时，单文件很快会膨胀成一份没人敢改的巨型说明书。


![多个技能通过共享状态协作的架构图](/images/posts/agent-skills-guide-2.svg)
GitHub 的 Data Forge 示例采用了一种更清楚的方式：让不同技能各管一段，再通过共享的项目状态协作。

| 技能 | 职责 | 产出或影响 |
|---|---|---|
| `forge-init` | 识别源表、命名规则等项目信息 | 写入 `resolved manifest` |
| `forge-builder` | 协调从 Issue 到 PR 的构建过程 | 调用查询与检查能力 |
| `forge-dbx` | 统一访问数据平台 | 根据配置选择 Databricks 或 DuckDB |
| `forge-lint` | 执行团队规范 | 在生成代码前检查设计约束 |

这里的 `resolved manifest` 可以理解成项目配置单。例如：

```yaml
name: "support-desk"
store_name: "support_metric_store"
pipeline_framework: "spark_python"
duckdb_dir: "warehouse"
```

`forge-init` 发现项目细节，`forge-builder` 读取它们，`forge-dbx` 根据配置选择执行环境。这样改一个项目时，只需替换配置，不必重写整套技能。

这个结构比让每个 Agent 独立摸索项目更稳，也比把所有规则塞进一份超长 `SKILL.md` 更容易维护。

## 项目配置和团队规则为什么要分开？

这是整套方法里最容易被忽略的一层。


![项目配置与团队规则分离及四步校验流程图](/images/posts/agent-skills-guide-3.svg)
**项目配置**回答「这次操作哪个项目」，例如数据仓库名称、指标存储位置、代码框架。**团队规则**回答「无论哪个项目都要怎么做」，例如命名规范、安全检查和审批要求。

前者适合放进 manifest，随项目变化。后者适合沉淀在技能里，让所有项目共享。

GitHub 官方示例特别提醒：仓库里发现的模式不自动等于团队规则。某个项目现存的命名方式，可能只是历史遗留。让 Agent 看到旧模式便照着复制，等于把偶然当规范复制一遍。

更稳妥的流程是：

1. `forge-init` 读取仓库现状，生成待确认的 manifest。
2. 人工检查名称、表结构和平台配置。
3. `forge-lint` 应用团队规则，标出不一致项。
4. 确认后的 manifest 才能进入后续构建。

这里多了人工确认，却少了一类很难查的返工：代码跑通了，但继承了旧项目里不该保留的坏习惯。

## “共享执行路径”到底共享什么？

多个技能都查询数据库，不代表它们应该共用一套连接代码。每个技能各写一份，最后会出现不同查询逻辑、凭据处理和错误处理。


![Data Forge 共享执行路径与运行边界架构图](/images/posts/agent-skills-guide-4.svg)
Data Forge 的做法是，让 `forge-dbx` 成为统一的数据访问路径。其他技能提出需要什么数据，由它读取 manifest，再选择 Databricks 或 DuckDB 等执行方式。

这样做有三个直接收益：

- 项目切换时，只改 manifest，不改每个技能。
- 凭据与连接逻辑集中管理，更容易审计。
- 查询失败时有统一错误格式，不必让模型猜哪里出错。

但要注意边界：**manifest 可以选择执行引擎，不能安装 DuckDB CLI，也不能授予数据库权限。** 工具、凭据和权限仍由运行环境提供。

技能文件像菜谱，运行环境才是厨房和钥匙。把钥匙写进菜谱，不会让厨房自动开门，只会扩大菜谱的暴露范围。

## 哪些地方必须留人工检查点？

GitHub 的 Data Forge 示例把流程分成七个阶段，每个阶段都有人工 checkpoint；执行前还会检查上一阶段是否完成，Schema 变更前则请求批准。

这一步很烦，但该留的时候不能省。适合设置检查点的位置通常有三个：

1. **事实发现之后**：Agent 已识别数据源，但还没决定业务含义。
2. **不可逆操作之前**：删除数据、修改 Schema、发布生产环境。
3. **质量判断有分歧时**：验证结果为 `PARTIAL`，需要人决定是否放行。

Proof Agent 的返回状态也值得借鉴：`PASS`、`FAIL`、`PARTIAL`，并附上证据。人工审批不应该只收到一句「我检查过了」，而要看到检查了什么、依据是什么、还有哪些不确定。

你甚至可以把检查点写成技能流程里的明确状态：

```text
proposed → needs-human-review → approved → executed → verified
```

Agent 可以自动完成 `proposed` 到 `needs-human-review`，但没有外部授权就不能越过审批状态。这样人工不是流程末尾的一句「确认一下」，而是一道有明确输入和输出的门。

## 一份可复制的技能检查清单

今晚准备沉淀技能时，可以直接复制下面这份清单：

```text
□ 这项技能只负责一个清晰任务
□ description 写明触发动作与交付物
□ 所有必填输入都有格式和缺失处理方式
□ 输出包含具体文件、字段或状态
□ 项目配置没有硬编码进技能
□ 团队规则与单个项目的偶然模式分开
□ 多个技能没有重复实现同一套工具逻辑
□ 不可逆操作前存在人工审批点
□ 验证结果附带可检查的证据
□ 技能目录已加入 Git，能够审查和回滚
```

再加一条最实用的测试：把技能交给一个没参与开发的人，只允许他读取仓库和 `SKILL.md`。如果对方还得来问你「数据库连接在哪」「失败后怎么继续」，说明流程仍在你的脑子，而不在文件里。

## Agent Skills 适合做什么，不适合做什么？

它适合有稳定边界的重复工作，例如发布检查、数据迁移、指标管线、报告生成和代码验证。

如果任务需要长期运行、强制权限、稳定接口或完整审计记录，单靠技能文件不够。GitHub 的建议是建设真正的应用程序：技能负责表达判断，应用程序负责执行约束和持续控制。

可以这样区分：

- 「遇到 PR 就按团队清单检查改动」适合做成技能。
- 「所有生产发布必须经过双人审批并永久留痕」更适合做成应用或 CI 流程。
- 「把这条口头说明告诉下一个 Agent」也适合做成技能。
- 「每天自动根据外部事件调整策略」需要长期控制，不只是技能。

Agent Skills 的价值，不在于把 AI 变得更神秘。它更像给一位每次入职都要重新培训的同事，递上一本写清楚的作业手册。谁都能看，谁都能改，出错时也能定位到具体哪一步。

你今晚不用整理全部经验。先找出本周解释次数最多的那个动作，写清触发时机、输入和输出，再给它加上第一个人工检查点。

等这份文件通过 Git 提交、团队评审，明天的你就不用把同一段话再打一遍了。

## FAQ

Q: SKILL.md 和普通 Prompt 有什么区别？<br>
A: Prompt 通常服务于一次对话，SKILL.md 是带版本管理的任务说明，可以包含触发条件、输入输出和执行路径，便于重复调用与团队共享。

Q: 一个技能可以包含多个任务吗？<br>
A: 可以，但最好按职责拆分。一个技能负责一个清晰任务，再通过共享配置或执行路径协作，通常比维护一份巨型说明更容易排查问题。

Q: 写完 SKILL.md 后，还需要配置工具和权限吗？<br>
A: 需要。技能只描述怎么做事，不会自动提供数据库连接、API 凭据或生产权限，这些仍要由运行环境和授权流程负责。
