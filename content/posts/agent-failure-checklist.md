假设你让 Agent 修一个登录按钮点了没反应的问题。它改了两处代码，跑了测试，终端一片绿，然后回你一句：已修复。

你刷新页面，再点一次。还是没反应。

这时候最麻烦的不是 bug 没修好，而是 Agent 已经用「测试通过」把这件事宣布完成了。你如果相信了那个结论，下一步不是排查登录按钮，而是排查一个根本不存在的结果。

Google AI 工程师 Patrick Kelly 最近开了一个叫 Where Agents Fail 的系列，专门拆这种「看起来做完了但其实没做对」的失败。首篇里，他分析了自己 <mark>160 次真实 Agent 会话</mark>，挑出 <mark>231 个具体错误</mark>。这个数字很扎心：Agent 的问题不只是不会做，而是它会自信地交付错误结果。原文在 DEV 社区发布，可见 [Where Agents Fail: Part 1](https://dev.to/)。

我倾向认为，这套失败模式最值得学的不是「模型还差得远」这种感慨，而是把它变成一份交付前自检清单。只要你还让 Agent 改代码、写文档、跑自动化，这张清单就能用。

## Agent 为什么会「修好了却没修好」？

因为它把局部信号当成了最终证明：测试过了、命令跑完了、回复写满了，于是它判断任务完成。但你要的是用户可见的结果，不是某一步执行成功。


![Agent局部信号与用户可见结果的错位对比](/images/posts/agent-failure-checklist.svg)
这三类错误里，第一种最危险。Agent 改完代码，测试套件通过，然后宣告一切正常。问题是，测试通过只能说明测试覆盖到的路径没炸，不能说明真实业务流程恢复了。尤其是 UI、权限、登录态、第三方回调这些地方，单元测试绿了，页面照样可能是坏的。

 Patrick Kelly 还提到一个公开 SWE-chat 数据集的早期信号：这个包含一万多个编码会话的数据集里，开发者报告失败的消息比例，从 2026 年初到夏天下降了大约三分之一。每次新模型出来，一部分老问题会消失，新的问题会冒出来。但「测试过了，功能没好」这类错，不会因为模型变聪明就自动绝迹。

原因很朴素。测试、构建、lint、静态检查，都是 Agent 能自己拿到的反馈；真实用户路径往往要人来判断。AI 会优先相信那些它不需要额外确认的信号。就像装修师傅量了墙、切了板、拍了照片，然后告诉你厨房能用了。你打开水龙头才发现没接上。

所以判断 Agent 是否完成，不能只问「它跑了哪些验证」，还要问「这些验证覆盖了用户看到的哪一段」。

## 三类高频翻车，长什么样？

这三类的共同点，是 Agent 都不是完全没干活，而是在错误边界上干得很积极。

| 失败模式 | 典型现场 | 真正的问题 | 你要防的是什么 |
|---|---|---|---|
| 假修复 | 测试通过、命令退出码为 0，但应用仍不可用 | 把局部验证当成业务验证 | 只信「用户路径复现」 |
| 越权多做 | 你只要方案或初步判断，它直接改代码、开 PR | 把请求理解成执行授权 | 把「分析」和「动手」分开说 |
| 反馈过度泛化 | 你说某个按钮太挤，它把全站按钮都改了 | 把局部反馈升级成全局规则 | 明确作用范围和例外 |

### 1. 假修复：测试绿了，功能还是坏的

这类错误有个很迷惑的外观：Agent 的报告非常像一次规范交付。

它会列出改了哪些文件、跑了哪些测试、结果多少通过，最后补一句「问题已解决」。如果你只看这份报告，几乎挑不出毛病。但报告和现实之间缺了一环：有没有回到最初那个失败场景，重新走一遍。

比如「导出按钮点了没反应」，测试可能覆盖了导出函数返回值，却没覆盖按钮是否绑定了事件；「接口偶发 500」，测试可能覆盖了正常请求，却没覆盖缓存过期时的并发路径。Agent 看到的绿色，是它选择的绿色。

我的判断是，假修复不是验证不够多，而是**验证对象错了**。让 Agent 多跑三套测试，未必比让它按用户步骤复现一次更有用。

一个简单约束足够有效：任务开始时，把验收标准写成一句用户能观察到的话。不是「修复登录问题」，而是「用测试账号 A 在登录页输入正确密码，点击登录后跳转到 /dashboard，且刷新后仍保持登录」。Agent 做完以后，必须针对这句话给出结果。

### 2. 越权多做：你问想法，它直接开工

这类翻车通常发生在需求表达得比较短的时候。

你说：「这个报错怎么处理？」你想听的是判断，甚至只是让它帮你梳理几种可能。Agent 却直接打开文件、改配置、补代码，顺手还把相关测试一起更新了。看起来很勤快，实际是把你还没确认的方案落到了仓库里。

原文把它归纳为 going further than you asked，这个描述很准。问题不在 Agent 能力强，而在它默认「用户提到问题＝希望我解决问题」。但对技术人来说，分析、设计、实施是三种不同动作。尤其在项目里，方案没确认就动手，后面清理成本可能比自己查还高。

这里不要靠语气暗示，直接写动作边界。比如：

> 只分析原因，不要修改任何文件。输出 3 个可能原因、每个判断依据、你建议我优先检查的位置。等我确认后再改代码。

这类提示词不花哨，但能把 Agent 从「自动员工」切回「可关闭的执行器」。我更愿意把 Agent 当成实习生：它可以很聪明，但你得告诉它今天是只读，还是可以写。

### 3. 反馈过度泛化：你改一处，它改全仓

第三个模式特别像职场里的「过度领会精神」。

你指出一个局部问题：「这个弹窗的确认按钮文案太硬，改柔和一点。」Agent 返回一长串修改：全站按钮文案统一、提示语风格重写、连错误状态也顺手调整了。你本来想修一句话，结果拿到了一次品牌语气迁移。

Patrick Kelly 把它叫 overcorrecting on feedback：你给的是窄反馈，它变成了全局规则。这种错误在文档、代码规范、UI 文案里都很常见，因为 Agent 会试图从一次反馈里推断「你偏好的长期原则」。推断有时是对的，但代价往往超出当前任务。

防这个坑的关键是给反馈加作用域。不要只说「太啰嗦」，要说「只改第三段，压缩到两句，其他段落保持不动」。不要只说「命名不好」，要说「只改这个组件内部变量，不改公共 API」。

这类约束看起来啰嗦，实际上是在帮 Agent 缩小世界。它少猜一点，你少返工一点。

## Agent 交付前自检清单，直接抄

下面这张清单可以直接放进你的项目 README、Agent 规则文件，或者每次任务末尾粘贴给 Agent。它不依赖某个具体模型，也不要求你换工具。


![Agent 交付前自检清单六步图](/images/posts/agent-failure-checklist-2.svg)
```text
Agent 交付前自检清单

1. 复述任务边界
   - 我的任务是什么？
   - 哪些文件/模块允许修改？
   - 哪些操作禁止执行（提交、开 PR、发邮件、改配置）？

2. 写出验收标准
   - 用一句用户可观察的话描述完成状态。
   - 不是「测试通过」，而是「用户执行 X 后看到 Y」。

3. 说明验证覆盖了什么
   - 我跑了哪些验证？
   - 每个验证覆盖哪条路径？
   - 哪些路径没有被覆盖？

4. 回到原始失败场景
   - 如果这是修 bug：按最初复现步骤重新走一遍。
   - 如果无法亲自走，说明缺少什么环境或权限。

5. 检查副作用
   - 是否修改了我没要求的范围？
   - 是否新增了全局规则、配置、依赖？
   - 是否把局部反馈推广到整个项目？

6. 报告结果格式
   - 已完成：
   - 验证方式：
   - 未验证/不确定：
   - 需要我确认：
```

我最看重第 3 和第 4 条。因为 Agent 最容易用一个成功信号替代全部现实，而这两条会逼它把「我做了什么」和「我证明了什么」分开说。

也可以把它压缩成一句提示词，放在每次任务结尾：

```text
在结束前，按以下格式报告：
1. 你改了什么；
2. 你验证了什么，验证覆盖了哪条用户路径；
3. 你没有验证什么；
4. 是否超出了我给定的任务边界。
不要只说「已完成」或「测试通过」。
```

这是个很朴素的办法，但比反复提醒「你要认真一点」有用得多。模型不听态度，模型听约束。

## 什么时候可以相信 Agent 说「修好了」？

当它能把结果绑定到你定义的验收路径上，并且明确说出未验证范围时，这个「修好了」才有参考价值。


![不同任务的验证标准对照图](/images/posts/agent-failure-checklist-3.svg)
我一般不会直接接受「已修复」「已完成」「测试全部通过」这三种表达。它们太像结束语了，信息量却很低。更有用的回答应该带着一点边界感：改了什么，验证到哪，哪里还没验证，需要人做什么。

这里还有个容易忽略的点：不同任务的验证标准不一样。文档任务看内容是否准确、术语是否一致；数据处理任务看样本输入输出是否对得上；自动化任务看异常分支有没有通知和回滚；编码任务看真实业务流程是否跑通。不能把所有任务都压缩成「命令没报错」。

Patrick Kelly 的系列还在继续，首篇只是把模式摆出来，后续会逐个研究能不能用今天的方法修复。这个方向我觉得比单纯追新模型更实在。模型升级当然会解决一部分老问题，但只要 Agent 还在替我们执行任务，边界、验证和副作用就不会过时。

说白了，Agent 最需要管的不是智商，是权限感。

## FAQ

**Q: Agent 说测试通过了，为什么还不能信？**<br>
A: 测试只覆盖被写进测试的路径。登录、支付、权限、UI 状态这类问题，可能测试全绿但用户路径仍是坏的。要按原始复现步骤再验一次。

**Q: 怎么防止 Agent 越权改文件？**<br>
A: 在任务开头明确写「只分析，不修改」或「只允许改某几个文件」。不要只靠语气暗示，也不要默认它会理解你的工作边界。

**Q: Agent 把局部反馈推广到全局怎么办？**<br>
A: 给反馈加作用域，例如「只改第三段」「只改这个组件」。结束前要求它报告是否超出任务边界，并检查新增配置和全局规则。
