假设你刚把 Python 升到 3.15，跑了一下之前一直好好的项目，屏幕上弹出一串错误：某个依赖构建失败，提示里还夹着一句你从没见过的「PyO3's maximum supported version」。你检查了代码，没改过。检查了依赖声明，也没动过。

问题大概率不在你改了什么，而在一个你从来没主动看过的文件：<mark>uv.lock</mark>。Simon Willison 昨天发了一篇短文，标题就一句话——「If in doubt, delete the uv.lock file」（拿不准就删掉 uv.lock）。他自己升级 Python 3.15 后反复遇到这种情况，最后总结出的处理方式简单到粗暴。

这篇文章讲清楚两件事：为什么删一个「锁版本」的文件反而能修好项目，以及什么时候删它会给你惹更大的麻烦。

---

## uv.lock 到底锁住了什么

用装修打比方：`pyproject.toml` 是你的装修意向清单——「我要地板、要瓷砖」，只写大类不写品牌型号；`uv.lock` 是装修公司的完整采购单——地板用哪个牌子哪个批次，螺丝买哪家，精确到每一个型号。


![pyproject.toml 与 uv.lock 的对比及其版本升级后的锁死效应](/images/posts/python-uv-lock-delete.svg)
这张采购单的用处是<mark>可复现</mark>：你在自己机器上装出来的环境，和别人、和 CI 机器上装出来的，一模一样。每次运行 `uv run` 或 `uv sync`，uv 都优先按这张采购单办事，而不是按意向清单重新询价。

问题出在采购单是快照。它记录的是「当时」解析出来的版本，而它不会自己更新。

所以当 Python 从 3.14 升到 3.15，你的锁文件里可能还钉着一个当时安装顺利、但现在没有 3.15 预编译包（wheel）的依赖。没有现成的预编译包，uv 就得退回源码编译；源码编译依赖构建工具链对 Python 版本的支持，比如 Willison 撞到的这个：

```
error: Failed to build `watchfiles==1.1.1`
error: the configured Python interpreter version (3.15) is newer
than PyO3's maximum supported version (3.14)
```

注意这里的荒诞之处：PyPI 上说不定早就有新版依赖支持 3.15 了，但你的锁文件钉死在旧版本上，uv 忠实地反复尝试安装一个注定装不上的东西。<mark>锁文件的本意是稳定，升级后却变成了牢笼。</mark>

删掉它，再跑一次 `uv run`，uv 会按意向清单重新解析一遍依赖，挑出当前 Python 版本下能装的最新组合——问题通常就这么消失了。

## 什么时候删，什么时候别碰

这个动作的前提是了解你的项目类型。一句话判断：


![uv.lock 锁文件处理决策指南与项目类型对比](/images/posts/python-uv-lock-delete-2.svg)
| 项目类型 | 有没有 uv.lock | 删了会怎样 |
|---|---|---|
| 应用 / 脚本 / 服务（自己跑的） | 通常有，且提交到仓库 | 一般可以删，重新生成即可 |
| 库（给别人 pip install 的） | 通常不该有 | 别删，也没必要删 |
| 团队 / CI 项目 | 有，且被提交 | 可以删，但要同步给全队 |

第三种要单独说。锁文件提交在仓库里，意味着它是团队环境一致性的契约。你本地删掉重新生成，提交回去，队友的环境就被你「升级」了——如果这次重解析顺带更新了其他依赖，别人的 bug 可能就是你埋的。



还有一个细节容易踩坑：如果你是库作者，`uv run pytest` 这类命令会在你的项目目录里悄悄生成 uv.lock（Willison 的做法是把它加进 `.gitignore`）。库不该替下游锁版本——那是使用方的事。所以库项目里的 uv.lock 删了就删了，零心理负担。

<div class="callout callout-tip">
💡 <strong>直接可用的排错清单</strong>：遇到依赖报错，按顺序试——① 看 `pyproject.toml` 是否声明过 requires-python；② 报错里出现「Failed to build」+ 某个具体版本号 → 九成是锁文件钉死了旧依赖；③ 备份后删 uv.lock，重跑 `uv run`；④ 用 `git diff uv.lock` 确认重解析的改动范围；⑤ 是库项目 → 直接删，不用犹豫。
</div>

## 为什么 AI 编程时代这事儿更常见了

这是我自己的判断，Willison 原文没提，但我觉得值得单独说。


![AI生成项目时锁文件冲突的风险与规避流程图](/images/posts/python-uv-lock-delete-3.svg)
锁文件问题的排查成本一直不低，因为它的症状极具欺骗性——报错指向某个具体的包构建失败，你的直觉会去查那个包、查系统环境、甚至重装 Python。很少有人第一反应是「去删一个我没编辑过的文件」。

而最近两年，越来越多人让 AI 直接生成或改造整个项目。AI 写 `pyproject.toml` 时经常顺手生成一份锁文件，或者用自己环境的 Python 版本做了解析基准——你拿过来一跑，版本对不上。这时候<mark>你对这份锁文件的来历一无所知</mark>，它的可信度反而更低。我的建议是：AI 生成的新项目，第一次跑之前先看一眼目录里有没有锁文件、它锁的解释器版本和你本机是否一致。

这个思路也解释了为什么「拿不准就删」在应用项目里是安全的：锁文件随时可以重新生成，它本来就是派生物，不是源。真正的源代码和依赖声明在你手里，锁文件坏了就再算一张，跟 `.gitignore` 了 build 产物是一个逻辑。

说到底，锁文件是一种缓存。缓存过期的时候，处理方式从来都一样——删掉，重建。<mark>只是它长得太像正经配置文件，没人舍得下手。</mark>下次 Python 升级后项目炸了，先看看那个文件。

## FAQ

**Q: uv.lock 和 requirements.txt 有什么区别？**<br>
A: requirements.txt 通常只列顶层依赖或冻结的完整清单，uv.lock 是 uv 工具自动解析、自动维护的完整依赖快照，支持跨平台哈希校验，保证每个环境装出完全一致的结果。

**Q: 删除 uv.lock 后需要重新提交到 Git 吗？**<br>
A: 如果锁文件原本在仓库里，重新生成后必须提交，否则队友和 CI 的环境会和你不一致。提交前用 git diff 检查版本变动范围，避免顺带升级无关依赖。

**Q: 库项目为什么不应该提交 uv.lock？**<br>
A: 库会被很多项目引用，锁死依赖版本会限制使用方的选择，甚至制造冲突。库只声明版本范围，把锁定版本的权力留给最终应用。
