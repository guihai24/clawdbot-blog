所有人都在比哪个模型更强、哪个 Agent 更能干，但很少有人指出一个尴尬的事实：<mark>Agent 的并发能力可以无限扩张，你的注意力不行。</mark>

DeepSeek 的 Harness 团队最近发了一篇文章，把这个痛点写得很直白：普通人只能同时跟进 3 到 5 个活跃会话。超过这个数，你就开始漏任务、忘进度、切错窗口。

有意思的是，大洋彼岸一家硅谷华人团队 AFK AI 半年前就把对应的解法做进了产品 Comma，而且开源了。两边在架构上不谋而合：一个主脑加一群干活的。

---

## 你的瓶颈到底是什么？

先还原一个典型的工作现场。

你让一个 AI 会话改代码，测试要跑十几分钟。客户突然催方案，你开第二个窗口。群里又有人问昨天的进度，你切回第三个窗口翻历史记录。十分钟后回头一看：代码那边测试报错了，方案写到一半，进度汇报的上下文你已经找不到了。

这不是模型不够聪明，是你这个「人肉调度器」过载了。

每一个会话都需要你做三件事：交代背景、盯过程、验收结果。三个会话是九件事，六个会话是十八件——而你的工作记忆大概只能装四件事。说得再狠一点：**你买的不是 AI 算力，你买的是一个需要全程人工看护的学徒团。**

解决方案的思路听起来有点绕：把「管理 Agent」这件事，也外包给 Agent。

---

## Router + 多 Worker：一个对话怎么管住十个任务

Super-agent 的核心架构其实只有两个角色：


![Router 主脑与多 Worker 协同架构及跨环境接力示意图](/images/posts/super-agent-router-worker.svg)
- **Router（主脑）**：常驻的主对话，负责接需求、拆任务、分派、汇总结果；
- **Worker（执行者）**：每个 Worker 有自己独立的上下文，在后台并行干活，干完汇报。

你只面对一个对话框。所有任务塞进去，Router 决定谁来做，Worker 各开各的上下文，互不污染。你随时可以插话加活、改需求，Router 负责把变化同步给对应的 Worker。

这解决的是三个老问题：

| 老问题 | 原来的样子 | Router 架构下 |
|---|---|---|
| 反复贴背景 | 每个新会话重新交代一遍 | 主对话记忆共享，任务自动携带上下文 |
| 满屏切窗口 | 6 个标签页来回切换 | 一个入口，进度汇总到同一处 |
| 任务排队干 | 一个会话干完才能接下一个 | 多 Worker 真并行 |

注意第二档术语：Worker 在这里指的是有独立上下文的专项子助手，类似 SubAgent（专项子助手）的概念——不是多开几个聊天窗口那种「假并行」，而是各自有独立工作区、真正同时推进。

### 跨环境接力：对话框之外它还能干活吗？

这才是 Super-agent 和「会话管理工具」的分水岭。

任务往往不只活在一个对话框里。需求记录在 Linear（项目管理工具）里，沟通发生在微信里，代码在 GitHub 上。原来的用法是你在这些平台之间来回搬运信息——现在 Router 统一承接各个渠道的消息，Worker 在后台执行，结果按原渠道返回。

Comma 的做法是接入了微信、Signal、iMessage、Linear 这些渠道，任务可以在平台之间接力：在对话里下达的项目需求，自动在 Linear 里建好 Issue；反过来，Linear 里的任务也能丢回给 Agent 执行，进展同步回原任务。

另一半能力是「持久」：就算你退出客户端、模型没在运行，值班程序仍然 7×24 盯着，到点或在关键时刻唤醒 Agent。比如给它安排一个长期任务——每天中午搜罗 AI 新闻整理成选题推送——到点消息自己送上门。

### 记忆放哪？这是比并行更难的题

会话越多，一个问题越尖锐：主对话的上下文窗口是有限的，任务细节全塞进去，很快就把记忆挤爆了。

Comma 的思路是把长期状态存在模型上下文之外，任务细节留给各自的 Worker，主对话只保留全局视图。更进一步，它把「持续学习」做进了产品：记录 Agent 的任务结果、人工修改和验收反馈，转化成训练信号去迭代专属小模型——新模型必须在内部评测里击败旧版本才能上岗。成熟工作流逐渐交给小模型，复杂任务继续用大模型。

这套机制是否足够可靠，我判断还需要更长时间的验证——目前公开的主要是团队自己的案例。但「让 Agent 从每次任务里积累经验」这个方向，我倾向认为是接下来一年 Agent 产品的必争之地。

## 怎么把这套东西用起来？

Comma 已于 9 月底开源（项目地址见 [AFK AI 的 GitHub](https://github.com/afkai) ⚠️ 仓库链接待确认），支持自部署和 BYOK（自带模型密钥），也能接入 Codex、Claude Code。上手前先想清楚一件事：**不是所有任务都值得交给常驻 Agent。**


![常驻 Agent 任务筛选与三类推荐场景](/images/posts/super-agent-router-worker-2.svg)
我整理了一张筛选清单，你可以直接对照着用：

```text
任务筛选三问：
1. 这个任务是重复发生的吗？（一次性任务直接丢给单个会话更快）
2. 我需要在固定时间或固定事件后触发它吗？（是 → 适合值班型任务）
3. 它的结果可以被描述和验收吗？（"每周五汇总本周进展"可以，
   "帮我想想职业规划"不行）
```

三类任务最适合先试：

- **定时盯梢型**：每天定点搜信息、汇总推送，接入微信或 Signal 接收；
- **跨平台搬运型**：对话里的需求自动建成 Issue，或反过来把 Issue 变成执行任务；
- **多线并行型**：同时推进写周报、整理资料、做小工具这类互不依赖的活。

<div class="callout callout-warn">
⚠️ <strong>权限先行</strong>：常驻 Agent 意味着它 24 小时能动你的账号。接入微信、Linear 前先想清楚给它什么权限、它能碰哪些信息——尤其是公司场景下的信息流控制，别等出事再补。
</div>

部署本身不算复杂，但涉及自有服务器和密钥配置，第一次跑通大概要花一个晚上。如果你不想折腾，也可以先观察各家大厂什么时候把类似机制做成开箱即用的产品——DeepSeek 这次发声，某种程度上就是在给这个方向定标准。

## 管结果，不管过程

最后说一个可以带走的认知转变。


![Agent心智模型对比：盯过程 vs 管结果](/images/posts/super-agent-router-worker-3.svg)
用单会话 Agent 时，你的心智模型是「盯过程」：它每一步做了什么、有没有跑偏，你都得看着。切到 Router 架构后，这个模型必须换掉——**你只定义任务和验收标准，中间的过程是 Router 和 Worker 的事。**

这跟带团队是同一个道理。什么样的领导最累？事必躬亲的那种。什么样的任务描述最有效？有明确交付物和判断标准的那种。

所以真正的上手门槛，其实不在部署，在你会不会写一份好的任务描述。今天就可以做个小实验：挑一件你最近重复做了三次以上的事，按「输入、触发条件、交付物、验收标准」四要素写清楚，然后想想——如果有个 7×24 在线、不会累也不会忘的实习生，这件事你还打算自己盯吗？

## FAQ

Q: 多开几个 AI 窗口不也能并行吗？<br>
A: 窗口并行的是模型，串行的是你。每个窗口的背景交代、进度跟进、结果验收都要你亲自做，任务一多注意力先崩，Router 架构把调度层也交给了 Agent。

Q: Comma 是免费开源的吗？<br>
A: 代码已开源，支持自部署和 BYOK（自带密钥），意味着模型费用取决于你接哪家模型。不想自部署的话，等托管版本或大厂同类产品也是选项。

Q: 这种架构适合什么人先用起来？<br>
A: 每天同时推进 3 个以上 AI 任务的重度用户最受益：独立开发者、做内容的人、技术向职场人。如果你一天只用一两次 AI，单会话反而更省心。
