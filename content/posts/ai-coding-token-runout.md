假设这一刻你的编辑器弹出一行字：本周期额度已用完，X 天后重置。

你手上要改的东西小得可怜——一个按钮文案、一个接口字段名、一处 CSS 间距。换成自己动手，可能两分钟。

问题只有一个：这两分钟，该花在哪个文件上。

V2EX 上今天有个帖子把这件事问得很直白：《当没 token 额度了 你会手改 AI 生成的代码吗》，发帖人 Misty99，35 条回复、2459 次浏览。评论区翻下来，是一份 AI 编程用户的自查表，而且是那种不太体面的自查表。

「改？我连他生成的代码在哪里放着都不知道。」

「改不了一点。AI 堆的屎山几千行，解铃还须系铃人，睡一觉等重置或者换中转。」

「我的水平已经不足以去修改 AI 大佬的代码了。尤其是克劳德老师的。😂」

也有人说实话：「如果是那种搜索替换文案的，或者改 css 样式的，可能还是会手动改一下，要是别的，那我宁愿去领一下免费的 token 来改。」

这里面藏着一个很少被说破的事实：**手改不是断粮时的应急手段，它是有额度时的一种习惯。** 有人把顺序说得很清楚——「没 token 了不会手动改，不过有 token 的时候会手动改下，都是改的比较小的，比如用 VSCode 批量搜索替换，高效还省 token」。

断粮那天才开始想手改，晚了。

## 断粮那天，你缺的不是手，是地图

先把「改不了」拆开。它其实是三种完全不同的失败。


![AI 协作中导致改不了代码的三种典型失败原因](/images/posts/ai-coding-token-runout.svg)
第一种，不知道在哪。「我连他生成的代码在哪里放着都不知道」——这跟懂不懂编程关系不大，跟有没有地图有关。AI 把功能实现得再漂亮，只要没告诉你它动了哪几个文件，这项目对你就是个黑盒。黑盒平时能用，一断电就废。

第二种，读得懂但不敢动。怕改坏，怕一改牵出三个报错，怕自己看不懂的那部分逻辑被自己踩塌。

第三种最阴——你改了，AI 给你改回去了。

帖子里有个例子具体到好笑：有人把一个页面的文件名从 index.html 改成 indext.html 做测试，后来用 AI 加功能时，AI 告诉他「文件被改了，已经帮你改回来了」。另一条回复紧跟着：「手动改了，AI 在执行的过程中，还会给我改回来，这种情况怎么处理？」

这不是 AI 有恶意。它每次动手前都会读一遍现场，发现现实和它记忆里不一致，第一反应是修复——而它记忆里那版，是它自己写的。**在没有交接记录的情况下，你的手动修改，在 AI 眼里就是一个待纠正的错误。**

所以断粮时真正困住你的，从来不是手速，也不是水平。

<mark>是这份代码里有没有给人留入口。</mark>

这个入口不是抽象的「可维护性」，是三件很具体的事：你知道哪个文件负责什么，你知道怎么把它跑起来，你知道改完怎么验证没坏。三件全缺，才叫「改不了一点」。

## 先问一句：你真的需要看懂这些代码吗？

我倾向认为，很多人在这里花错了力气。


![项目生命周期与代码理解策略对比图](/images/posts/ai-coding-token-runout-2.svg)
不是所有项目都值得你去看懂。判断标准不在代码质量，在这个项目还要活多久。

| 项目状态 | 典型例子 | 要不要看懂 |
|---|---|---|
| 一次性工具 | 爬虫脚本、批量改名、给客户临时跑的 demo | 不需要。跑通就交付，坏了重写 |
| 要活三个月以上 | 自己的小产品、每周都在加功能 | 需要最小可维护面 |
| 要交给别人 | 收钱的、多人协作的、要部署上线的 | 必须有，没得商量 |

中间那档最容易被忽略，也最要命。它不够「小」到可以扔掉重写，又不够「大」到让你认真做工程规范。评论区那句「对于一个 70% 以上的 vibe coding 项目来说，手改是不存在的」，对一次性项目成立，对这类项目是灾难。

所谓最小可维护面，指的不是读懂全部代码，而是一个很小的集合：能说清项目的入口文件是哪个、启动命令是什么、数据存在哪里、某个具体功能大概落在哪几个文件里。有了这四件事，你就能在额度耗尽时定位到改动点、验证改动是否生效；没有这四件事，代码写得再漂亮，对你也是一个只能运行、不能修改的黑盒。

## 三类改动：能接手的、该降级的、必须等额度的

有了最小可维护面，下一步才是分流。判断成本的关键不是「难不难」，是「改坏了你能不能立刻看出来」。


![三类改动分流标准与处理策略对比图](/images/posts/ai-coding-token-runout-3.svg)
| 类型 | 典型例子 | 断粮时怎么办 | 判断标准 |
|---|---|---|---|
| 表层替换 | 文案、颜色、间距、图片路径、接口地址、环境变量 | 自己改，或全局搜索替换 | 改完刷新页面就能看见差别 |
| 局部逻辑 | 一个 if 条件、一处报错兜底、一个字段映射 | 降级到免费或低价模型 | 你能一句话说清改前改后 |
| 结构改动 | 加模块、换框架、加数据表字段、改鉴权方式 | 攒着，等额度 | 要动三个以上文件，或动完不知道从哪测 |

中间那栏的标准是全篇最实用的一条：**能不能用一句话说清「改前是什么、改后是什么」。说得清，算局部改动；说不清，算结构改动，别碰。**

原因很朴素。说得清，你脑子里就有一个可验证的预期，改完自己点一遍就知道对不对。说不清，你只能靠「看着没报错」判断——那不叫验证，叫赌。

再补一句诚实的：有些局部逻辑改起来比等额度还贵。一个报错卡两小时，那这两小时不如去干别的活，晚上等重置。

## 应急五步：把剩余额度花在「买地图」上

额度见底时，人的本能是赶紧再让 AI 写点功能。这是最差的用法。剩下的那点额度，应该花在「解释」上，不是「生成」上。

第一步，买地图。

趁你还有一两次对话，让它把项目讲清楚，并且明确禁止它改代码。这段可以直接抄：

```
读完这个项目，只输出一份地图，不要改任何代码，控制在 300 字以内：
1. 入口文件是哪个，本地启动命令是什么
2. 数据从哪来、存到哪去，分别涉及哪几个文件
3. 如果要改【你要改的那个功能】，需要动哪几个文件，按顺序列出
4. 改完之后，怎么验证它没坏
```

更好的时机是每次功能做完、额度还充足的时候跑一次，把结果存成项目根目录的一个文本文件。成本是一次对话，收益是下次断粮时不用从零开始找。

第二步，让它解释，别让它写。

读不懂的段落直接圈出来问：「这段在干什么，如果我想把里面的 X 从 A 改成 B，最小改动是什么？」注意后半句。要求「最小改动」，它就不会顺手重构你整个函数。

第三步，缩小战场。

一次只改一个文件、一个函数。别在断粮的时候顺手清理代码，那不是省事，是给自己埋雷。

第四步，改之前先留底。

一行 `git commit`，或者干脆复制一份文件出来。这一步人人都知道，人人都跳过，然后人人都后悔。

第五步，用搜索代替理解。

大部分表层改动根本不需要读懂代码，只需要找到它。

- Mac：VS Code 里 `⌘ + ⇧ + F` 全局搜索，或在项目根目录跑 `grep -rn "要改的文字" .`
- Windows：`Ctrl + Shift + F`，命令行用 `findstr /s /n "要改的文字" *`

搜到之后看上下文三五行，确认是那处，再动手。命中多个文件就先改一处、刷新验证、再改下一处。

## 手改完被 AI 改回去，怎么办？

这是评论区里最多人踩、最少人解决的坑。解法不是「别手改」，是把你的改动变成 AI 读得到的事实。

三个动作，按顺序做。

改完立刻提交。有 commit 就有历史，AI 改乱了你至少能回滚，也能让它看 diff 对着改。

在项目根目录放一份「人类改动记录」。不用复杂，一个 Markdown 文件就够：哪一天、改了哪个文件、为什么改、别再动它。有人用 AGENTS.md 这类约定文件，形式不重要，关键是每次开工前让它先读。

在 prompt 里加一句「先读 [文件名]，里面记录了手动改过的地方，不要覆盖」。这句话能挡掉大部分「善意回滚」。

说白了，AI 不是不听话，是不知道。你不告诉它，它只能按自己记忆里的版本修复世界。

## 换便宜模型不是应急，是一次迟到的实验

帖子里有句话被当成玩笑：「大不了换个便宜模型哈哈。」

我判断这句话里有一半是真话，而且是很多人一直拖着没做的一次实验。

断粮逼你做的事，本质是一次成本审计——你被迫验证，那些你以为「必须用最强模型」的活，到底有多少是真的需要。评论区已经有人给出了答案：「我现在甚至改个 ui 文本都让 ai 干了，反正各个 flash 版本都很快的。」



但别把降级当万能药。涉及架构设计、多文件联动、疑难报错的活儿，降级只会换来来回回的返工。分流的判断标准和前面那张表是一样的：说得清改前改后，降级；说不清，等额度。

<div class="callout callout-tip">
💡 <strong>一个省钱习惯</strong>：把「探索」和「执行」拆开。理思路、定方案用最强模型，改文案、调样式、跑小修补用快模型。同一件事分两段做，成本能降一大截，结果反而不受影响。
</div>

## 最后一句

回到开头那两分钟。

你改不了一个按钮文案，不是因为你不会写代码，是因为这个项目里没有一条从「我要改什么」通向「它在哪」的路。这条路不是断粮那天修的，是每次让 AI 写完功能后多问一句「你动了哪几个文件、怎么验证」修出来的。

今天能做的最小一件事：打开你最近那个项目，让它给你画一份地图，存成文件。趁你还有额度。

## FAQ

**Q: 额度用完了，多开几个账号继续不就行了？**<br>
A: 大多数平台的条款不允许绕过额度限制，把项目进度押在这上面风险不划算。更重要的问题是：这只能推迟断粮，不会让代码变得可维护。

**Q: AI 写的代码我完全看不懂，还有救吗？**<br>
A: 有。别从「读懂全部代码」开始，从「能跑起来」这条线开始：入口文件、启动命令、数据存在哪、某个功能落在哪几个文件。四件事问清楚，就有得救。

**Q: 手改会不会让 AI 之后改得更乱？**<br>
A: 会，如果你不告诉它。用 commit 留痕，再放一份人类改动记录让它先读，基本能避免它把你的修改当错误修复掉。
