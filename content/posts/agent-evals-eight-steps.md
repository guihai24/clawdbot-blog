一个 Agent 在 demo 里答得漂亮，不等于它适合放进产品。

demo 通常只展示最顺的那条路：问题清楚、材料干净、工具每步都返回预期结果。真实用户会把文件命名成 `最终版真的最终版.xlsx`，会在中途改需求，会在 Agent 已经调用完工具后又补一句「刚才那个别算」。

这时候如果你还靠「我感觉它挺聪明」来判断能不能上线，交付质量就变成了抽奖。

我在意的不是 Agent 能不能完成一次漂亮回答，而是它能不能在你说不清的那堆边角情况里，仍然稳定地接近目标。<mark>Agent 评测就是把「像会的」压缩成「可复核的」。</mark>

Hugging Face 官方博客在 2026 年 11 月 23 日发了一篇《How to build and maintain an agentic evaluation》，用物理实验室里的拉曼光谱拟合任务 [raman-lab](https://huggingface.co/spaces/raman-lab/raman-lab) 做例子，拆出一套八步流程。原文在 [Hugging Face](https://huggingface.co/blog/agentic-evals)。

我不打算把它翻成说明书。更值得抄的是这套顺序背后的判断：**先写清楚你到底要 Agent 做什么，再决定拿什么题考它，最后才轮到模型和提示词。**

---

## 为什么 Agent 不能只靠 demo 判断效果？

因为 demo 验证的是「能不能做到一次」，产品需要的是「在一类任务里有多常做到」。


![Demo 单次验证与线上产品评测的对比](/images/posts/agent-evals-eight-steps.svg)
普通问答评测像考选择题：给一个问题，看一个答案。单 Agent 评测要管理上下文、工具调用和多轮状态，评分不能只看最后一句话。多 Agent 系统更像一个团队，任务怎么拆、成员怎么交接、谁来收口，都会影响结果。

举个很具体的场景。你做了一个客服 Agent，能查订单、改地址、退差价。demo 里用户说「帮我改地址」，它查到订单、调用接口、返回成功，看起来很稳。

但线上用户可能说：

- 「我上周搬走了，那个东西别寄老地方。」
- 「地址先别改，万一今天发货呢？」
- 「我改完地址，运费是不是也算错了？」

这几句话都在考同一件事：Agent 有没有理解任务边界，知道哪些操作能做，哪些要先停下来问人。仅靠一次 demo，你根本看不到这些。

所以评测不是上线前补的一份文档，而是把产品风险提前变成题目。

## Agent 评测到底要评什么？

一句话：评 Agent 在特定任务范围内，能否用合适步骤得到可接受结果，并且失败时别乱来。


![Agent 评测三层级对比与风险提示](/images/posts/agent-evals-eight-steps-2.svg)
这里有三个层级，差别很大：

| 层级 | 主要评什么 | 常见坑 |
|---|---|---|
| 问答 | 答案是否事实正确、格式对不对 | 只看最终文本，忽略依据 |
| 单 Agent | 工具调用、状态管理、多轮决策 | 中间步骤错了一步，最后碰巧蒙对 |
| 多 Agent | 分工、交接、汇总、冲突处理 | 成员各自很忙，整体没人负责 |

问答评测里，错了就是错了。单 Agent 不一样，它可能会绕路、重试、调用错工具后再修正。最后答案对，不代表过程可信；最后答案错，也不一定每一步都没价值。

多 Agent 更容易制造一种错觉：日志里很热闹，每个 Agent 都输出了一堆内容，但用户真正要的结果没人收口。评这类系统，不能只看每个成员的局部表现，还要看团队层面有没有把任务闭环。

<mark>最贵的错误，不一定是最难的错误。</mark>一个模型解不出复杂光谱拟合，顶多这次任务失败；但一个 Agent 在权限边界上乱调用工具，可能直接把产品拖进事故里。评测题里要把后者单独标出来。

## raman-lab 的八步法，怎么用到自己的 Agent 上？

Hugging Face 的 raman-lab 案例做的是拉曼光谱拟合：系统要读取实验数据，调用工具，调整参数，给出拟合结果。这个任务离普通业务很远，但流程很适合迁移。


![Agent 评测八步法流程图](/images/posts/agent-evals-eight-steps-3.svg)
下面是改造后的通用版本。你可以把它套到客服 Agent、数据分析 Agent、爬虫自动化、DevOps 助手上。

### 1. 先写能力声明，不要先写 prompt

能力声明就是一句话说清楚：这个 Agent 负责什么，不负责什么。

比如：

```text
本 Agent 负责根据用户问题查询订单状态，并在用户明确确认后修改收货地址。
它不负责退款、优惠券补发、价格争议判断；遇到权限不足或信息冲突时必须转人工。
```

这句话看着朴素，但它决定后面的评测范围。如果能力声明里没写「不负责退款」，你后面就没法稳定地判断「用户问退款时它硬答」到底是 bug 还是锅太大。

写不出来，说明 Agent 的产品边界还没想清楚。这时候继续调 prompt，基本是在给雾里开车换轮胎。

### 2. 把能力拆成可评分的任务

别一上来就做几百道题。先把能力声明拆成几类任务：

- 正常路径：用户表达清楚，工具返回正常。
- 模糊表达：用户说得不完整，需要追问。
- 拒绝路径：用户请求超出范围，Agent 要明确拒绝或转人。
- 工具异常：接口超时、返回空值、数据格式不符。
- 多轮变化：用户中途改主意，前文信息需要更新。

每类先写 3-5 道题，就够跑第一轮。

这里有个判断标准：<mark>看到题目后，你能说出「正确答案应该长什么样」。</mark>如果你自己都说不清，就别把它放进第一批评测集。

### 3. 给任务设一票否决项

不是所有错误都一样。

客服 Agent 改错地址，是严重错误；回答时语气不够温柔，是体验问题。代码助手删掉用户没要求删的文件，是严重错误；解释少了一句背景，是表达问题。

建议每题标三类结果：

| 结果类型 | 含义 | 处理方式 |
|---|---|---|
| 通过 | 结果和关键步骤都符合预期 | 计入通过率 |
| 部分通过 | 结果勉强对，但过程有风险 | 进入迭代清单 |
| 一票否决 | 越权、误操作、编造关键事实 | 单独统计，优先修 |

一票否决项要和普通错误分开。否则一个 Agent 靠大量简单题刷高分，却在关键场景里反复越线，报表上看着还挺体面。

### 4. 选模型时，别只看排行榜

Hugging Face 的原文案例对比了多个模型。这一步的重点不是「哪个模型最强」，而是「哪个模型在你的任务集上最稳」。

你可以固定同一套 prompt、工具定义和评测题，只替换模型，记录四件事：

- 最终答案是否正确。
- 工具调用是否必要且顺序合理。
- 失败时是否会停下来澄清。
- 单题成本和延迟是否可接受。

我更倾向把模型当成候选员工，不是神。排行榜说明它简历好看，你的评测集才说明它适不适合这个岗位。

### 5. 同时评「结果」和「轨迹」

Agent 评测最容易偷懒的地方，是只看最终答案。

假设你让 Agent 查订单。它没调用订单工具，而是根据用户名和城市猜了一个地址，最后居然猜对了。这题算过吗？我不算。

轨迹评测要看它有没有用对工具、有没有在信息不足时追问、有没有在工具报错后做合理处理。Hugging Face 这类 agentic evaluation 的价值就在这里：它把过程从黑盒里拽出来。

你可以先用最简单的手工表格记录：

```text
题目编号：
用户输入：
预期结果：
实际结果：
关键步骤是否合规：
是否越权/编造：
失败原因分类：
```

别嫌土。早期评测最怕一上来搭大平台，最后只产出一堆没人看的仪表盘。

### 6. 用「失败原因」驱动修改

评测跑完，不要只盯着分数。分数只能告诉你坏了，失败原因才能告诉你哪里坏。

常见失败原因可以分成这几类：

- 能力声明没覆盖：题目超出边界，Agent 不知道该拒绝。
- prompt 表达含糊：规则写了，但 Agent 没把它当硬约束。
- 工具描述不清：模型不知道什么时候该用哪个工具。
- 上下文污染：多轮对话里旧信息压过了新信息。
- 模型能力不足：任务确实超过当前模型稳定处理范围。

不同原因对应不同动作。工具描述不清，改工具说明；上下文污染，做状态压缩或重述；模型能力不足，才考虑换模型。

说白了，评测不是扣分，是把「提示词再调调」拆成具体维修单。

### 7. 留出封存题，防止自己骗自己

当你反复看同一批错题、反复改 prompt，很容易把评测集调成自己的训练集。最后分数上去了，线上还是翻车。

做法很简单：把评测题分成两组。

- 开发集：平时拿来定位问题、改 prompt。
- 封存集：固定时间才跑，平时不看具体错题。

如果你只有 20 道题，至少留 5 道封存。不要嫌少，封存的意义不是统计显著，而是提醒你别把答案背下来。

这也是我从旧文盲测那类方法里借来的判断：**验证集一旦被你天天摸，它就不再像真实用户。**

### 8. 把评测变成维护任务，而不是一次性仪式

Agent 上线以后，三件事会变：用户说法会变，工具接口会变，模型版本也会变。

所以评测要跟着版本走。每次改 prompt、换模型、加工具、调权限边界，都跑一次固定评测。结果不一定要全量公开，但至少留一份记录：版本号、通过率、一票否决项、典型失败样例。

你可以把它塞进现有的发布流程里，不必单独搞一套重体系：

```text
发布前：
1. 跑开发集，定位明显回归。
2. 跑封存集，确认没有背题式优化。
3. 检查一票否决项是否为 0。
4. 记录模型版本、prompt 版本、工具版本。
5. 若出现新失败样例，先补题，再修复。
```

评测维护的难点不是技术，是纪律。因为它不会像线上报警那样催你，直到某次用户投诉，你才发现这套表三个月没人打开过。

## 怎么把评测结果用到模型和提示词迭代？

别用平均分做决策，用失败类型做决策。


![故障地图到迭代动作的映射图](/images/posts/agent-evals-eight-steps-4.svg)


我判断这是很多团队做 Agent 评测时会走偏的地方：他们把评测做成排行榜，追求一个漂亮数字。但产品迭代需要的是故障地图。

你更应该盯这几列：

| 观察项 | 下一步动作 |
|---|---|
| 简单题也错 | 检查基础 prompt 和工具描述 |
| 只在多轮后错 | 检查上下文压缩和状态更新 |
| 换模型后波动大 | 固化关键规则，降低对模型发挥的依赖 |
| 一票否决项出现 | 暂停发布，先加硬约束或人工确认 |
| 某类题反复错 | 补题、归类，再决定是改提示词还是改流程 |

这里还有个原文没展开、但我觉得很现实的点：**Agent 评测会反向暴露产品需求是否清楚。**

如果一批题你死活写不出标准答案，原因常常不是模型不行，而是业务规则本来就没人拍板。比如「什么情况下可以自动改地址」这件事，客服、运营、法务各有说法。评测集一写就吵架，其实是好事，它把组织里的模糊要求逼到纸面上。

## 一个最小可跑的评测模板

如果你今天就要开始，不要等平台，不要等预算。先用这张表跑 20 道题。

```text
Agent 能力声明：
- 负责：
- 不负责：
- 必须转人工的情况：

评测任务：
1. 正常路径：
2. 模糊表达：
3. 越权请求：
4. 工具异常：
5. 多轮变化：

每题记录：
- 用户输入：
- 预期结果：
- 允许调用的工具：
- 禁止发生的行为：
- 实际结果：
- 关键步骤是否合规：
- 失败原因分类：
- 是否一票否决：

发布门槛：
- 开发集通过率达到内部约定线
- 封存集无重大回退
- 一票否决项为 0
- 所有新失败样例已补题
```

这套表不高级，但能逼你回答三个问题：Agent 该做什么、怎么算做对、错了以后先修哪里。

等到题目稳定了，再上自动化、上 dashboard、上专门平台。顺序反了，工具越多越乱。

## FAQ

**Q: Agent 评测和普通 Prompt 测试有什么区别？**<br>
A: 普通测试多看最终回答，Agent 评测还要看工具调用、多轮状态和失败边界，重点是过程是否可信。

**Q: 评测集一开始要做多少题？**<br>
A: 先做 20 道左右，覆盖正常、模糊、越权、工具异常和多轮变化。能稳定评分，比数量大更重要。

**Q: 什么时候该换模型？**<br>
A: 先看失败原因。若提示词、工具描述和流程都修过仍失败，再在同一评测集上对比候选模型。

别再问「这个 Agent 看起来聪不聪明」。

今天把它的能力声明写出来，再挑 5 个正常场景、5 个麻烦场景、5 个它绝对不该碰的场景，让它跑一遍。你会马上知道，该庆祝的是它的答案，还是该补的是你的规则。
