假设你正盯着屏幕发愁，手头有一个挺有意思的小创意：想做一个能把普通照片瞬间变成复古油画的网页小工具，但又不想去配复杂的前端打包环境、不想装一堆臃肿的 NPM 库。

大多数人的第一反应是：这得去翻 Canvas API 手册，或者找个现成的图形渲染库来啃。但如果换个思路，把整个图像算法的实现和前端布局全权交给大模型，事情会变成什么样？

最近，知名技术博主 Simon Willison 晒出了他的一个新玩法：他只用了一句精心构造的 Prompt，丢给 Claude Opus 5.5 High，就直接拿到了一款基于原生 Canvas、支持 Sobel 边缘检测的网页油画模拟器。整个过程没有任何多余的外部库，打开浏览器就能直接跑。

对想快速验证创意、做点有趣独立产品的技术人来说，这种“用纯粹的 Prompt 驱动原生浏览器能力”的玩法，究竟藏着怎样的技巧？

## 为什么说“零外部依赖”才是小工具开发的王牌？

很多人在用大模型写网页代码时，习惯性地让 AI 引入 React、Tailwind 甚至是复杂的图形库。结果往往是一堆依赖冲突、版本报错，还没开始写核心逻辑，光是配环境就花了两小时。


![零外部依赖小工具开发的优势与原生能力对比](/images/posts/prompt-to-canvas-oil-painter-generator.svg)
而真正的轻量化玩法，是**把浏览器的原生能力压榨到极致**。

在 Simon Willison 的这次实验中，他并没有让 Claude 去调用沉重的第三方画图框架，而是直接指定了纯 `<canvas>` 元素。这意味着什么？这意味着所有的数据处理——从像素矩阵的读取、色彩梯度的计算，到模拟画笔轨迹的渲染——全部在浏览器的原生内存中高效流转。

对于独立开发者来说，零外部依赖意味着三个致命优势：
1. **秒级交付**：AI 生成的代码是一个单文件 HTML，直接丢进浏览器就能运行。
2. **零维护成本**：没有依赖包更新带来的安全漏洞，也不用担心 NPM 仓库哪天又出什么幺蛾子。
3. **极佳的定制性**：当你想修改画笔的粗细、落笔的角度或色彩混合的权重时，直接对着这段原生 JavaScript 调整即可，没有任何框架抽象层的阻碍。

## 怎么用一句 Prompt 把视觉算法转译给 AI？

要想让大模型一次性吐出能用的代码，最忌讳的是含糊其辞的描述。如果你只是说“帮我写个油画效果”，AI 大概率会给你一个粗糙的 CSS 滤镜交差。


![高质量视觉算法Prompt的三要素结构图](/images/posts/prompt-to-canvas-oil-painter-generator-2.svg)
关键在于**在 Prompt 中明确技术路径与底层算法**。

复盘这套 Prompt 的核心结构，你会发现它包含了三个硬核要素：

首先是**明确的容器与渲染目标**："Build an artifact where you open a photo and it rapidly (in a few seconds) paints a version of that photo using a canvas element and simulated paintbrush"。这里直接锁死了 UI 交互形式（Artifact）和核心载体（Canvas）。

其次是**指明算法方向**。在后续的实现中，它采用了经典且轻量的 Sobel 边缘检测算法。通过在 Prompt 中或者让 AI 自行补充这种计算机视觉的基础算子，模型写出来的代码才不是简单的“马赛克滤镜”，而是真正能识别图片轮廓、根据梯度走向来安排笔触方向的仿真引擎。

最后是**严苛的性能约束**："rapidly (in a few seconds)"。这个时间锚点极为重要，它在提示词层面逼迫 AI 优化循环效率，避免在处理大分辨率图片时导致主线程直接卡死。

## 独立开发者如何复刻这种“提示词驱动工程”？

看到这里，你可能会问：这不就是日常的 vibe coding 吗？有什么好特别的？


![独立开发者提示词驱动工程的三步标准操作流程](/images/posts/prompt-to-canvas-oil-painter-generator-3.svg)
区别在于你是否在用大模型替代“脏活累活”，而不是替代思考。

在尝试用这个思路开发自己的小工具时，你可以遵循这样一套标准操作：

首先，界定边界。不要试图用一句话让 AI 帮你做一个美图秀秀。每次只挑一个核心视觉特效来做，比如“单图素描转换器”、“像素风实时降采样器”或者“网页端简易白板”。

其次，限定技术栈。在 Prompt 明确加上“纯 HTML/CSS/JavaScript，不使用任何外部库，所有逻辑写在一个文件内”。这样能把大模型的注意力全部集中在算法实现和 DOM 交互上，而不是浪费在模块导入上。

最后，利用迭代闭环。拿到初版代码后，先上传一张测试图片跑一下。如果发现边缘渲染太粗糙，不要自己去改代码，而是把报错或视觉缺陷反馈给 AI：“Sobel 算子的阈值太高了，导致细小线条丢失，请优化梯度计算逻辑并加快渲染速度。”

## 常见问题与踩坑指南

Q: 为什么 AI 生成的 Canvas 渲染大图时会卡死页面？<br>
A: 因为像素级的矩阵运算如果全塞在主线程同步执行，必然会阻塞 UI。解决办法是让 AI 把图片降采样到合理尺寸（例如最大边限制在 800 像素以内），或者分片（requestAnimationFrame）异步渲染。

Q: 除了油画，这种纯 Canvas 模式还能用来做什么工具？<br>
A: 非常适合做各类轻量级多媒体处理工具，比如网页端表情包生成器、SVG 路径动画调试器、或者是独立游戏里的简易粒子特效预览面板。

Q: 为什么一定要用 Claude Artifact 这种形式？<br>
A: 因为它能在对话右侧直接实时预览运行效果，省去了你本地建 `index.html`、配置本地服务器的繁琐步骤，极大地缩短了“想法验证”的闭环周期。
