「我本地跑过了。」

这句话在开发群出现的频率，大概和「这个需求很简单」差不多。它是程序员最诚实的自我安慰，也是产品上线后第一个 bug 的墓志铭。

本地跑过的意思是：你打开过那个页面，点过那两下，确认它没白屏。但真实用户会在 Safari 里用中文输入法填手机号，会在支付回调返回前把标签页切走，会在第三步按浏览器后退键——然后发现加购的数量还在，购物车的金额没了。

<mark>AI 把写代码的时间压到一个下午，然后把这堆场景原封不动留给了你。</mark>

一个人做产品，最难的不是开业，是试营业那天没人来。餐厅老板开业前会请朋友把菜单全点一遍，不是不信任厨师，是厨房到餐桌这段路只有真跑一遍才知道哪里堵。你的登录、加购、支付，就是那桌菜。

## 写代码变快了，验证为什么没变快？

先说结论：**验证的成本从来不在「写测试」，在「养测试」。**


![传统测试与AI时代下UI高频变动导致测试成本飙升的恶性循环对比图](/images/posts/ai-e2e-testing-momentic.svg)
Momentic 官网首页顶上来就是一句话：「Code moves faster. Verification has to keep up.」这句不是营销，是这次发布的题眼。它来自 YC W24 的一家旧金山公司，产品叫 Mo，定位是「AI QA 工程师」——你描述用户流程，它在真实浏览器里跑。

为什么偏偏是现在做这件事？因为 AI 编程把迭代频率拉高了。以前一个项目一周发一次，现在一个下午改三轮。UI 结构跟着代码一起高频变动，而传统测试是绑在选择器上的：一个 `data-testid` 改了名，二十条用例一起红。

红第一次你会修。红第三次你会跳过。红第五次你会在 CI 里把它标成「允许失败」。

这才是独立开发者放弃测试的真相——不是懒，是投入产出比算不过来。你总共几十个用户，修测试的两小时不如去拉一个新用户。

但产品一旦碰到钱和权限，这笔账就反过来了。

## 传统 E2E 测试，为什么独立开发者一试就放弃？

答案很朴素：写得出来，养不起。Playwright 和 Cypress 本身不难，难的是三个月后你还认不认得自己写的那堆选择器。


![传统选择器测试与 AI 意图测试的维护成本对比](/images/posts/ai-e2e-testing-momentic-2.svg)
端到端（E2E）测试的初衷是模拟真人操作：填表单、点按钮、看结果。听着简单，落地全是细节。加一个 loading 遮罩，点击被拦截，超时；换一套按钮组件，`#submit-btn` 找不到了；某个接口慢了三秒，断言的时机不对，报了个「元素不可见」。

这些都不是 bug，是测试自己坏了。而判断「这是应用 bug、测试脆弱、还是环境问题」，恰恰是最耗人工的部分——你得打开截图、翻 trace（浏览器执行轨迹）、复现一遍，才能确定该改代码还是改测试。

有一个设计上的取舍值得说清楚：**选择器让测试变得精确，也让测试变得脆弱。** 精确是你想要的，脆弱是你付出的代价。UI 越常改，代价越高。

![传统选择器测试与自然语言测试的维护成本对比](/images/posts/ai-e2e-testing-momentic.svg)

Momentic 换了个思路：测试不绑选择器，绑意图。

## 把一条用户流程，写成一句人话

先给一个自包含的说法，方便你判断这东西到底是什么。


![自然语言端到端测试的YAML结构与三大设计点](/images/posts/ai-e2e-testing-momentic-3.svg)
> 自然语言端到端测试，指的是把「打开首页、登录、加购、填地址、支付、看到订单号」这样的用户流程，用接近人话的 YAML（靠缩进表示层级的配置文件）写下来，交给 AI 在真实浏览器里执行，失败时给出截图、trace 和出错的那一步。它替代的是 Playwright、Cypress 这类要写选择器的脚本测试；它不替代单元测试，也不负责判断界面好不好看。适合已经能跑起来、有真实付费流程的产品，不适合还在天天改原型的阶段。

官方示例里那份结账流程，长这样：

```yaml
fileType: momentic/test/v2
id: standard-user-checkout
url: https://shop.your-app.com
description: 标准用户从登录到下单的完整流程

steps:
  - module: ./log-in.module.yaml
  - act: 把第一个商品加入购物车，进入结算页
  - module: ./fill-personal-info.module.yaml
  - assert: 每一项的小计与商品标价一致
  - click: 提交订单
  - assert: 订单状态为「已支付」，且金额等于购物车总额
```

三个设计点值得拆开看，因为它们各自解决了一个具体麻烦。

**第一是 module。** 登录流程抽成 `log-in.module.yaml`，几十条测试共用一份。改登录页的时候你只改一个文件，全部用例跟着生效。这一条直接打掉了「维护成本随用例数线性增长」这个老问题。

**第二是知识库。** 你可以在里面写术语表、预期行为、测试指引，AI 每到一步就去查。不然它不知道你们产品里「优惠码」和「折扣码」指的是同一个东西，也不知道「已支付」和「支付成功」哪个才是页面上的真实文案。

**第三是失败证据分级。** 它会把失败分成应用 bug、测试不稳定、环境问题三类，配上出错那一屏的截图和 trace。这件事人工做要十几分钟，机器做是几秒钟——而且它不会被你昨天的情绪影响判断。

## 让 coding agent 自己写测试，是这次发布里最值得抄的部分

大多数人用 AI 测试工具的方式是：人写测试，机器跑。


![Coding Agent 与 Momentic MCP 闭环测试流程图](/images/posts/ai-e2e-testing-momentic-4.svg)
Momentic 想推的是反过来的：**写代码的那个 agent，顺手把验证也做了。**

它提供了 MCP（让 AI 工具互相连接的协议）接入。逻辑是，你的 coding agent 改完一个功能，可以立刻调 Momentic 去写一条对应的测试、在真实浏览器里跑一遍、看失败截图，然后判断是自己代码写错了还是测试写错了。测试的 YAML 文件跟代码存在同一个仓库，一起提交，一起 review。

这段话可以直接丢给你的 coding agent：

```
你刚改完了【结账页的优惠码逻辑】。
1. 用 Momentic 的 MCP，把「登录 → 加购 → 输入优惠码 → 支付」这条流程写成测试
2. 在真实浏览器会话里跑一遍
3. 如果失败，先看截图和 trace，判断是应用 bug、测试脆弱还是环境问题
4. 如果是应用 bug，改代码，不要改测试
5. 通过后把 YAML 存到 tests/ 目录，和这次改动一起提交
```

第 4 条是整段话里最重要的一句，原因下一节说。

<div class="callout callout-tip">
💡 <strong>为什么要把测试放进仓库</strong>：测试写在别人的云平台上，agent 读不到、review 看不到、diff 里也没有。写成 YAML 存进 repo，它就和代码一样受版本控制——改了什么、谁改的、为什么改，全有记录。
</div>

## 自愈省了事，也可能把 bug 一起「修」掉

这是我最想提醒的一段，也是官网不会主动展开的部分。

自动修复（healing）的机制是：UI 变了，AI 重新找到那个控件，让测试继续跑下去。这解决的是「测试自己坏掉」的问题。

但如果测试失败的原因是**真 bug**——比如提交按钮被一个错误的权限判断变成了不可点——AI 也可能「重新找到」另一个可点的元素，绕过去，测试变绿。

于是 bug 顺利上线，而你以为自己验过了。

Momentic 的做法是把永久性修复做成「提案」，需要你 review 才会写回测试文件。这个设计是对的，但它默认了一个前提：**你愿意看那些提案。**

<div class="callout callout-warn">
⚠️ <strong>一条硬规则</strong>：每条测试至少要有一个 assert，而且这个 assert 必须落在用户能感知的东西上——金额、数量、订单号、页面状态。只有点击没有断言的测试，等于让 AI 在页面里散步，走完什么都没验证。
</div>

判断标准可以更具体一点：如果你的测试写的是「点击提交按钮」，那它只验证了「按钮存在」。改成「提交后订单状态显示为已支付，且金额等于购物车总额」，它才开始验证业务。

## 一个人做产品，最小可用的测试该测什么？

不要一上来写二十条。五条稳定的，比二十条三天就红的值钱得多。优先级按「坏了会不会死人」排：

| 优先级 | 流程 | 为什么排这个位置 | 断言什么 |
|---|---|---|---|
| P0 | 注册 / 登录 / 找回密码 | 全站入口，坏了等于关门 | 登录后能看到自己的邮箱或昵称 |
| P0 | 完整付费路径：加购 → 填信息 → 支付 → 订单页 | 直接等于收入 | 订单号、金额、订单状态三者对得上 |
| P1 | 写进去的数据能不能读回来 | 最高频的「看着成功其实没存」 | 刷新页面后数据还在，且内容一致 |
| P1 | 权限边界：未登录访问、访问别人的数据 | 出一次就是事故 | 该拦的拦住了，且拦得对 |
| P2 | 空状态和异常状态 | 决定第一印象 | 空列表有引导文案，不是白屏 |

P0 那两条必须跑在每次合并之前。

接入 CI 的方式很轻：把它的命令行工具放进 CI job，用退出码当必过检查。命令具体怎么写以官方文档为准，但落地的形式就一句话——测试挂了，合并按钮是灰的。 这比任何自觉都可靠。

成本这块我不猜。官网有免费试用入口，付费档位和额度按其官网为准，我不清楚具体价格，所以给个更实用的建议：先用免费额度把两条 P0 跑稳，跑一个月，看它到底抓到过几次真问题。抓到过，再谈升级。

## 什么该交给 AI 测，什么不该

这类工具解决的是「流程能不能走通」，不是「好不好用」。边界很清楚：

- 不适合：视觉回归（那是截图对比的活）、性能压测、文案是否得体、交互是否顺手。
- 需要额外准备：真实的第三方回调。支付、短信验证码、OAuth 授权，这些绕不过沙箱环境和测试账号，AI 也变不出来。
- 要小心：移动端 App。官网提供了 Android 相关的示例，但真机环境比浏览器复杂得多，先从 Web 跑通再考虑。

我不太确定这类「AI 跑测试」在超大型项目里最终会稳定到什么程度。测试用例上千条之后，AI 判断失败原因的准确率会不会下降，没有公开的长期数据。官网挂了一份 QA Bench 报告，用 1,396 条标注过的 bug 做基准，参评的包括 Mo、Codex、Claude Code 和 Devin——具体结论我没法替它转述，值得自己翻一遍再决定。

但对你一个人做的产品来说，这个量级远未到。你需要的不是最强的测试系统，是「每次改完代码，有人替你把登录和支付点一遍」。

## 最后一句

回到那家餐厅。开业那天没人替你点单，但你可以提前一晚把菜单全点一遍——从冷盘到甜品，包括那个你自己都没吃过的。

今晚就可以做一件事：打开你的产品，把登录流程用一句话描述出来，写成第一条测试，跑一遍。

它大概率第一次跑不过。那就是你明天要修的第一个 bug。

## FAQ

Q: 自然语言测试靠谱吗，会不会经常误报？<br>
A: 误报主要来自断言写得太模糊。把断言落在金额、数量、订单号这类确定性数据上，误报会少很多。官方也提供了把失败分成应用 bug、测试不稳定、环境问题三类的机制。

Q: 一个人开发，值得为测试工具花钱吗？<br>
A: 先看你的产品是否涉及付费或用户数据。涉及，就值得——一次线上支付故障的损失通常远超工具年费。不涉及，先用免费额度跑两条核心流程观察一个月。

Q: 它和 Playwright、Cypress 是替代关系吗？<br>
A: 在端到端这一层是替代关系。单元测试、集成测试仍然需要你自己写。区别在于前者绑选择器、要写代码，后者写自然语言、由 AI 执行并在 UI 变动时自动修复。
