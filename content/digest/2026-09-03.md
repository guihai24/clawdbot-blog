#### 1）今天最值得关注

**[3名工程师用0行手写代码发布产品，核心是"harness工程"]**
- **发生了什么**：Google 工程师 Shir Meir Lador 分享实验——**3人团队用 Codex 编写了全部代码**（应用逻辑、测试、CI配置、文档、可观测性和内部工具），发布了内部 beta 产品，手动编写代码量为 **0 行**。核心方法不是写业务逻辑，而是设计包裹 LLM 的确定性组件环境，即 harness engineering。
- **为什么重要**：这标志着 coding agent 的范式转移——开发者角色从"写代码"变为"设计环境"。harness 包括编排层、执行沙箱、状态持久化和验证工具，让 agent 无需逐行人工审查即可安全生成代码。
- **我的判断**：这是长期趋势，不是短期噪音。所有依赖 agent 写代码的团队都应该现在就开始研究 harness 设计，否则下个月就会落后。
- **关键数据**：**3 名工程师**、**0 行手动代码**、迭代超过 **5 次**时触发 kill switch（`iteration_count > 5`）。
- **来源**：[Google AI：DEV 作者专属（RSS）](https://dev.to/googleai/what-is-harness-engineering-and-why-should-i-care-8n0)

#### 2）硬核技术 / 产品动态

- **[Anthropic 开源电商 Agent 参考实现，附生产架构指南]**
  - **事实**：Anthropic 发布《有效商业代理解剖指南》，开源 `anthropics/commerce-agents` 参考实现，含购物 Agent 与商家 Agent，基于与零售、旅游、电信等行业团队的生产经验总结。
  - **看点**：架构核心是**单个 Claude 在标准 Agent 循环中配合技能与工具**，而非按领域拆分子智能体，也不含意图路由器——这是对多智能体狂热的一种纠偏。
  - **对老大的启发**：如果你在做电商、零售类 Agent，直接参考这个开源实现可以省掉数周架构摸索时间，指南覆盖了延迟、成本、内存、安全、评估和组织扩展三个维度。
  - **来源**：[Claude：Blog（网页）](https://claude.com/blog/the-anatomy-of-effective-commerce-agents)

- **[Google AI 分享 LLM-as-a-Judge 可靠评分标准编写四原则]**
  - **事实**：Google AI 团队发布教程，讲解如何为 LLM-as-a-Judge 评测编写可靠的布尔式评分标准，强调模糊提示会导致评估不一致并浪费 token 预算。
  - **看点**：<mark>问题必须原子化且互不重叠、只评估客观事实（可用 RFC 2119 术语如 MUST 表述）、只评 prompt 中明确要求的内容、用专家标注校准</mark>——四条原则直指当前 Agent 评测中最常见的四个坑。
  - **对老大的启发**：如果你在用 LLM 做评估或打分，这篇教程能直接帮你减少无效 token 消耗和评估噪声，建议团队评测流程中强制执行这四条。
  - **来源**：[Google AI：DEV 作者专属（RSS）](https://dev.to/googleai/how-to-write-reliable-rubrics-for-llm-as-a-judge-evaluations-ndp)

- **[Google DeepMind 发布 Gemini 3.8 Flash 与 3.8 Flash Cyber 两款新模型]**
  - **事实**：Google DeepMind 正式发布 Gemini 3.8 Flash 和 Gemini 3.8 Flash Cyber 两个新模型。
  - **看点**：Flash 系列持续迭代，Cyber 变体针对安全/对抗场景优化，适合需要高可靠性的 Agent 部署。
  - **对老大的启发**：如果你的产品对延迟和成本敏感，Flash 系列仍是首选；Cyber 变体值得在安全敏感场景做对比评测。
  - **来源**：[Google DeepMind：Blog（RSS）](https://deepmind.google/blog/introducing-gemini-3-8-flash-and-38-flash-cyber)

- **[OpenAI 团队分享 AI-native 公司如何将工作流转化为运营能力]**
  - **事实**：OpenAI Blog 报道 Basis、Clay、Exa Labs 等 AI-native 公司使用 AI Agent 改进入职、客户管理和开发者体验。
  - **看点**：这些公司的共同点是 Agent 不是辅助工具，而是核心运营能力——从招聘到客户支持的完整链条都由 Agent 驱动。
  - **对老大的启发**：独立开发者可以参考这些案例，思考哪些重复性工作流可以用 Agent 替代，而不是只把 AI 用在产品功能上。
  - **来源**：[OpenAI Blog](https://openai.com/index/ai-native-company-workflows)

#### 3）可执行机会

- **机会标题**：为小团队构建"Agent 代码审查 harness"SaaS
- **痛点**：越来越多团队用 Codex、Claude Code 等 agent 生成代码，但没人逐行审查——Google 的实验证明 harness 是关键，但中小团队没有工程资源自己搭。
- **怎么做**：做一个轻量 SaaS，输入 GitHub 仓库，自动注入编排层、执行沙箱、测试验证节点和 kill switch，输出一个可复用的 harness 配置（基于 Google ADK 2.0 或类似框架）。
- **为什么值得做**：这是 harness engineering 趋势的早期基础设施需求，先做的人能卡位。收费模式可以是按仓库/月订阅，目标客户是用 agent 写代码但没人做 code review 的 5-50 人团队。
- **最小起步版**：先用 Google ADK 2.0 的 Workflow 图实现一个模板，支持"agent 生成代码 → 自动跑测试 → 失败自动反馈修复 → 超过 5 次迭代自动终止"的完整循环，部署为一个 GitHub Action，第一个月免费给 10 个早期用户。

<div class="callout callout-tip">💡 <strong>起步建议</strong>：不要一开始就做通用 harness，先专注一个场景——比如"agent 生成 PR 后的自动测试+修复循环"，跑通后再扩展。</div>
