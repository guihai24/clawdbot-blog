#### 1）今天最值得关注

**Gemini API 上线 Tool Retrieval：工具库不再全量塞进每一次请求**

- **发生了什么**：Google 在 Gemini API 的 Interactions API 中推出 Tool Retrieval，目前处于 preview。启用方式是在请求里加一个 `tool_search` 工具，并对需要延迟加载的工具设置 `defer_loading: true`。模型仍然能看到每个工具的名称和描述，但参数 schema 不进入上下文，模型按名称点名后由服务端加载完整 schema，再发起函数调用，全程在同一个请求内完成。支持 Gemini 3.6 及以上模型。
- **为什么重要**：对做 agent 的人，这是把"工具选择"从静态提示工程变成检索问题。**对编程**：工具数超过二三十个之后，schema 占掉的输入 token 和选择准确率会同时恶化，这个方案正面打这两点。**对产品**：远程 MCP 服务器上设一个 `defer_loading` 就能让整台服务器的工具按需加载，接第三方集成不用再逐个手写声明。**对独立开发者/SaaS 变现**：工具接入成本降下来，"一家人人有几十个集成的 agent 产品"从工程上变得可行，中间层的套壳空间会被压缩，但同时上线垂直场景 agent 的门槛也低了。
- **我的判断**：这是长期趋势，不是噪音。真正的信号是<mark>主流 API 开始承认 prompt 装不下工具库</mark>。值得马上跟进的原因是它几乎没有迁移成本——代码改动只是加工具加标志。但注意两个边界：搜索跑在 Gemini 服务端，换模型栈这条能力就没了；客户端检索模式（声明 `"execution": "client"`）才是自建工具注册表和按用户权限过滤场景的答案，这块要自己写。
- **关键数据**：preview 阶段；支持 **Gemini 3.6 及更高版本**；示例代码使用 `gemini-4-hydrogen`；Tool Retrieval **无单独收费**，输入/输出 token 按所调用模型标准费率计费；兼容前缀缓存（延迟的 schema 不在 prompt 开头，缓存前缀逐轮保持一致）；搜索、schema 加载、函数调用三步都出现在 `interaction.steps` 里可查。
- **来源**：[Google AI Blog](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/)

#### 2）硬核技术 / 产品动态

- **Browser Use 拆解计算机使用类智能体：四步循环 + 三种界面读取方式**
  - **事实**：Browser Use 的作者 Nik Tomazic 在 11 月 19 日发布科普文章，把 computer use 类智能体的运行拆成**读取界面 → 选择动作 → 执行 → 验证**四个环节，并比较了**截图、DOM、无障碍树**三种读取界面的方式，分别说明优劣与适用场景。
  - **看点**：三种读取方式不是互相替代关系，而是各有代价——原文明确把它列为"按场景权衡"的问题，而不是选一个默认方案。同一个循环里被最容易跳过的是最后一环"验证"，它不是一个可选项，而是流程的一部分。文章还把速度与成本列为独立考量维度，说明快不等于便宜、便宜不等于准。安全上给出两条明确建议：**限制权限**、**防范提示词注入**。
  - **对老大的启发**：如果你在给客户做流程自动化的 agent，别从"能不能点"开始设计，从"点完之后怎么确认点对了"开始设计——验证环节决定了这套东西能不能交付给非技术用户。
  - **来源**：[AIHOT · Browser Use](https://aihot.news/items/jbu3hudzri98k423yk9zhbcp4) ⚠️ 原文未给出速度、成本、准确率等任何量化指标，本条不含性能数据

- **OpenAI 用 Codex 搭了个自动找性能回归并直接开 PR 的工厂**
  - **事实**：OpenAI 公布内部的 Performance Factory，一个跑在云端的自主系统，用 Codex 和自家模型自动调查并修复 ChatGPT 的性能问题。团队多年积累了**超过 30 个性能工具**（CPU 与内存分配 profiler 等），并把调查流程固化成一个叫 `perf-forensics` 的共享 skill，告诉 Codex 有哪些工具、什么时候用、从哪几个角度看一次变慢：定位变慢从何时开始、找出受影响的请求、排查部署和配置变更。
  - **看点**：整条链路是"告警 → 诊断（经过对抗式审查）→ Codex 实现修复并开 PR → 工程师 review 合并 → 输出回归影响、根因、修复方案的报告"；如果修复没带来改善，agent 会记录下来并把任务退回。真正值得抄的是它的评估设计：<mark>把"调查过程"和"总结报告"分开评</mark>，报告用保存的任务快照加独立 grader 检查——判据是"一个不熟悉这项任务的工程师能否从图表和证据看懂下一步该干什么"。另外它会把反复出现的失败转成自修复任务：同一个工具错误卡住多次调查，agent 就自己建任务去修工具。
  - **对老大的启发**：这套方法可以直接搬到你自己的 cron + 监控上——不是让 agent 修 bug，而是让 agent 把"为什么变慢了"的证据链整理到人能三分钟看懂的程度，这本身就已经值回成本。注意它当前的瓶颈是等工程师 review 和合并，Agent 能自己写不能自己上线，这个边界短期内不会变。
  - **来源**：[OpenAI Blog](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast)

#### 3）可执行机会

- **机会标题**：给"工具太多"的 agent 做一个跨模型的本地工具检索层
- **痛点**：今天 Gemini 的方案只服务于 Gemini 模型和它的服务端。而现实里大多数独立开发者的 agent 跑在多家模型上、工具来自多个 MCP 服务器，工具数一过二三十个，prompt 里塞满 schema，输入 token 账单和选错工具的概率一起上升。没有一个中立的、跟模型厂商无关的中间层来解决这件事。
- **怎么做**：一个轻量中间层库。输入是所有 MCP 服务器或 OpenAPI 描述，输出只暴露两个函数给主模型：`search_tools(query)` 和 `call_tool(name, args)`。工具的名称和描述进 embedding 索引，schema 存在本地，被点名时才注入上下文。附带三件低成本但很值钱的事：按用户权限过滤可见工具、记录每次检索命中率、把注入的工具 schema 做前缀缓存友好的排序。
- **为什么值得做**：省 token 是立竿见影的成本项，能直接算给客户看；降选错工具率是效果项。变现路径清楚——开源核心库引流，托管版按调用量或按接入的 MCP 服务器数收费，卖给正在把 agent 接进企业内部系统的小团队。
- **最小起步版**：先做一个 Python 包，只支持一个 MCP 服务器 + OpenAI 风格 function calling，跑通"检索 → 注入 → 调用"三段，附一个能对比"全量注入 vs 检索注入"token 消耗的基准脚本。这个对比数字就是你后面所有内容的第一张图。
